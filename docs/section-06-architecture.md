# Раздел 6. Как это держится вместе

> Черновик для статьи (часть 2). Короткий, «в поддержку»: не витрина фич, а фундамент. Почему всё распилено на слои, что такое data-driven NPC и — главный практический вопрос — **как добавить второго персонажа, не переписывая проект**.

В части 1 всё было единым куском кода вокруг одного героя. Это нормально для PoC и невыносимо для развития: любая новая идея тянула за собой правку всего. Во второй части мы развели ответственность по слоям так, чтобы каждый слой можно было менять отдельно.

---

## 6.1. Четыре слоя

```
   ┌──────────────────────────────────────────────────────────────┐
   │  4. ДАННЫЕ NPC        DataAsset + Resources/NPCs/<имя>/        │
   │     (кто это, что умеет, как звучит)   ← правит гейм-дизайнер  │
   ├──────────────────────────────────────────────────────────────┤
   │  3. ЛОГИКА NPC        Blueprint: ActionHandler, DataGetter     │
   │     (что делает действие, откуда контекст) ← правит разработчик│
   ├──────────────────────────────────────────────────────────────┤
   │  2. СКЛЕЙКА           игровой C++ модуль (NpcData, реестр,     │
   │     (общий каркас)     эмоции, структуры)                      │
   ├──────────────────────────────────────────────────────────────┤
   │  1. ТЕХНОЛОГИИ        плагины: ULlamaPlugin (LLM+RAG),         │
   │     (переиспользуемое)  TTS, LipSync                           │
   └──────────────────────────────────────────────────────────────┘
```

Чем выше слой — тем чаще его трогают и тем меньше для этого нужно быть программистом. Чем ниже — тем стабильнее и универсальнее. Пройдёмся снизу вверх.

---

## 6.2. Слой 1: технологии = плагины

Всё «тяжёлое» вынесено в отдельные плагины, каждый из которых ничего не знает про торговца и вообще про игру:

- **ULlamaPlugin** — инференс LLM поверх `llama.cpp` и база знаний (эмбеддинги, поиск).
- **TTS** (SpeechGenerationSystem) — синтез и клонирование голоса.
- **LipSync** (ULSS) — анимация губ MetaHuman по аудио.

Смысл разделения простой: **плагин переиспользуется**. Тот же ULlamaPlugin можно вставить в другой проект, а TTS и LipSync полезны и сами по себе (они и живут отдельно, в том числе на Marketplace). Игра зависит от плагинов — плагины от игры не зависят.

> Небольшой, но приятный инженерный штрих внутри ULlamaPlugin: физическая модель (веса) **загружается один раз и разделяется** между всеми NPC, использующими её, через подсчёт ссылок. Десять торговцев на одной модели — это одна модель в памяти, а не десять. Подробнее о цене моделей — в разделе 7.

---

## 6.3. Слой 2: склейка

Тонкий C++ модуль игры, который соединяет плагины с данными и говорит на языке предметной области, а не библиотек. Здесь живут:

- **описание NPC** (`UNPCDataAsset`) и **реестр** всех персонажей (`UNPCDataRegistry`) — «телефонная книга»: по имени получить данные любого NPC;
- **структуры ответа и запроса** (эмоция, действие, параметры);
- **перечень эмоций** и хелперы к ним.

Это клей. Он не решает, *что* сказать торговец, — он лишь даёт остальным слоям общий словарь.

---

## 6.4. Слой 3: логика — точки расширения в Blueprint

Здесь ключевое архитектурное решение: **вся специфика персонажа выносится в Blueprint через два расширяемых класса.** Программист на C++ не нужен, чтобы описать поведение конкретного NPC.

```
   ┌─────────────────────┐        ┌─────────────────────────┐
   │  ActionHandler       │        │  DataGetter              │
   │  «что физически      │        │  «откуда брать контекст» │
   │   делает действие»   │        │                          │
   │  Execute(VM, name,   │        │  GetNpcState / GetUserState
   │          params)     │        │                          │
   └─────────────────────┘        └─────────────────────────┘
        колонна «действует»            колонна «живёт»
```

Оба — абстрактные, расширяемые в Blueprint. Причём **DataGetter универсален по источнику**: откуда он берёт данные — дело разработчика. Сейчас это игровая логика (инвентарь, здоровье), но с тем же успехом там может быть запрос в базу, обращение к внешнему сервису или что угодно ещё — контракт («верни строку состояния») остаётся прежним.

---

## 6.5. Слой 4: данные — data-driven NPC

Верхний слой — то, ради чего всё затевалось. Персонаж описывается **данными**, а не кодом:

- в **DataAsset** — имя, личность, список действий, сэмплы голоса по эмоциям, привязка обработчиков и геттеров;
- в **`Resources/NPCs/<имя>/`** — сгенерированные из этого описания артефакты: системный промпт и грамматика (`chat/inference_cfg.json`), база знаний (`emb/knowledge_base.json`), а также LoRA-адаптер (`lora.gguf`).

Как мы уже отмечали в разделах 3 и 4, **эти артефакты не пишутся руками** — они собираются из описания NPC автоматическим пайплайном (тема части 3). Дизайнер работает с человекочитаемым DataAsset, а не с грамматиками и эмбеддингами.

---

## 6.6. Проверка на прочность: добавить второго NPC

Лучший тест архитектуры — вопрос «сколько стоит второй персонаж». В части 1 — переписать половину проекта. Здесь:

```
   Хочу нового NPC — механика-оружейника
        │
        ├─ 1. Новый DataAsset: имя, характер, действия, голоса   (дизайнер)
        ├─ 2. Прогнать пайплайн → промпт, грамматика, база, LoRA (авто)
        ├─ 3. ActionHandler'ы под его действия                    (Blueprint)
        └─ 4. DataGetter'ы под его контекст                       (Blueprint)

   Слои 1–2 (плагины и склейка) НЕ трогаем вообще.
```

Технологический фундамент и общий каркас остаются нетронутыми. Меняются только данные и — если у персонажа есть уникальные действия — их обработчики. Это и есть смысл всей перестройки: **NPC стал контентом, а не кодом.**

---

## Итог раздела

Четыре слоя, каждый со своей скоростью изменений:

1. **Плагины** — переиспользуемые технологии, живут отдельно от игры.
2. **Склейка** — общий словарь предметной области.
3. **Логика** — ActionHandler и DataGetter, расширяются в Blueprint.
4. **Данные** — DataAsset + сгенерированные ресурсы; NPC как контент.

Благодаря этому второй, третий и десятый персонаж — это работа дизайнера, а не рефакторинг движка.

Осталось честно поговорить о том, где всё это буксует, — раздел 7.

## Заметки автора (не для публикации)

- Слой 1 (плагины): ULlamaPlugin, ULSS (LipSync), SpeechGenerationSystem (TTS). Есть ещё `uqsgs` — уточнить его роль, если стоит упоминать.
- Разделяемая модель с подсчётом ссылок: `FULlamaModelRegistry` в `ULlamaManager.cpp` (Acquire/Release, ключ по `ModelFilePath|Lora|GpuLayers|NCtx`). Хороший факт для раздела 7 (память). Здесь подан мельком — не углубляться.
- Слой 2: `UNPCDataAsset`, `UNPCDataRegistry` (`GetNpcData`/`GetNpcDataJson`), `FLlmResponseData`/`FUserRequestData`, `ENpcEmotion`.
- Слой 3: `UULlamaActionHandlerBase::Execute`, `UKnowledgeBaseDataGetterBase::GetNpcState/GetUserState` — оба Abstract/Blueprintable/EditInlineNew.
- Слой 4: `Resources/NPCs/<npc>/chat/inference_cfg.json` (+ lora.gguf), `emb/knowledge_base.json`. Привязка ActionHandler/DataGetter — в `FNpcActionTemplate` внутри DataAsset.
- Не углубляться в MVVM здесь (это раздел 4/5). В слоях UI отдельно не выделял, чтобы не плодить сущности; при желании добавить как под-слой представления над «данными».
- Факт-чек: действительно ли сейчас в проекте больше одного NPC, или второй персонаж — гипотетический. Раздел 6.6 подан как «стоимость добавления», это работает в обоих случаях, но формулировку сверить.
