# Статья, часть 2 — рабочий план

**Тема:** от «говорящей головы» (PoC из части 1) к живому и полезному NPC.
**Часть 1:** https://habr.com/ru/articles/807561/ (PoC: UE 5.3, Vosk + Mistral 7B + Piper + Oculus LipSync + MetaHuman).

## Параметры (согласовано)

- **Гвоздь двойной:** NPC, который *действует* (function calling) + NPC, который *живёт* (RAG + эмоции).
- **Формат:** мало кода, много схем. Единственный уместный листинг — формат действий / GBNF.
- **Аудитория:** смешанная (как ч.1) — бережно объясняем термины и со стороны LLM, и со стороны UE.
- **Сквозной пример:** один — NPC-торговец.

## Сквозная идея

> В части 1 персонаж научился *говорить*. В части 2 он научился **помнить, чувствовать и действовать** — перестал быть «говорящей головой» и стал участником игры.

Две несущие колонны:
- **Живой** → RAG (память фактов) + эмоции (голос / мимика).
- **Полезный** → function calling (влияет на игровой мир).

## Арка трилогии (важно держать в голове)

Финал ч.2 (раздел «грабли») готовит почву для ч.3:

> Маленькие модели ошибаются и плохо тянут длинную историю чата → в части 3 автоматически дообучаем **LoRA-адаптер под конкретного NPC**, опираясь на его описание в DataAsset.

Крючки, которые уже есть в коде и их стоит «подсветить» заранее:
- `FULlamaInferenceConfig.LoraAdapterFilePath` — слот под адаптер уже заложен.
- Data-driven описание NPC (`UNPCDataAsset`) — будущий источник обучающей выборки.

### 3. Колонна I — NPC, который живёт
- **3.1 Память: RAG внутри движка.**
  - Проблема «золотой рыбки»: модель не знает фактов мира.
  - База знаний → эмбеддинги → семантический поиск → релевантные факты в промпт.
  - Аналогия для смешанной аудитории: «шпаргалка перед ответом».
  - Схема: запрос → поиск → факты в контекст.
- **3.2 Эмоции: голос и лицо.**
  - Модель возвращает эмоцию → выбор голоса под эмоцию → мимика MetaHuman + LipSync.
  - 5 эмоций (Neutral/Happy/Sad/Angry/Surprise).
  - Схема связки эмоция → голос → лицо.
  - Почему стриминг предложений в TTS важен для «живости» (латентность).

### 4. Колонна II — NPC, который действует *(ключевой раздел)*
- **4.1 Проблема:** как надёжно заставить текстовую модель дёргать игровую логику.
- **4.2 Решение:** триггеры-действия в ответе (`ExtractTrigger`) + GBNF-грамматика для парсибельного вывода — «наш function calling».
  - Здесь единственный уместный фрагмент кода: формат действия / кусок грамматики.
- **4.3 От намерения к эффекту:** `ActionHandler` → MVVM → реальный UI. Схема потока.

### 5. Сквозной пример — торговец *(кульминация)*
- Одна фраза игрока, трассировка через все системы:
  STT → RAG → LLM → эмоция + триггер → TTS + LipSync → действие над инвентарём → UI обновился.
- Таймлайн-диаграмма «жизни одной реплики» — склеивает обе колонны.

### 6. Как это держится вместе *(архитектура — коротко, в поддержку)*
- Почему распилили на плагины (ULlamaPlugin / TTS / LipSync).
- Data-driven NPC: дизайнер собирает персонажа без кода (Data Assets + JSON).
- Диаграмма модулей, без глубокого кода.

### 7. Грабли и производительность *(честный раздел — и мост в ч.3)*
- **Маленькие модели ошибаются** (галлюцинации, неверные триггеры/параметры).
- **Плохо тянут длинную историю чата** с игроком (лимит контекста `NCtx`, управление историей `bResetHistory`).
- Латентность и как боролись (стриминг, sentence-chunking в TTS).
- CPU vs GPU (CUDA / `GpuLayers`).
- Что НЕ получилось.
