# Раздел 3. NPC, который живёт

> Черновик для статьи (часть 2). Первая из двух колонн: как персонаж обрёл **память, понимание и характер**. Вторую колонну — как он научился *действовать* — разберём в разделе 4.

Живость складывается из двух вещей. Во-первых, NPC должен **знать факты своего мира** и не выдумывать их на ходу. Во-вторых, он должен **проявлять характер** — звучать и выглядеть по-разному в зависимости от настроения. Разберём по очереди.

---

## 3.1. Память: RAG внутри движка

### Проблема «золотой рыбки»

Языковая модель сама по себе не знает про ваш мир ровным счётом ничего. Зато врёт с обезоруживающей уверенностью. Спросите торговца, есть ли у него железный топор и почём — и маленькая модель, глазом не моргнув, назовёт цену, которую только что сочинила. Спросите ещё раз через минуту — цена будет другая. И товар, возможно, тоже.

Наш NPC в этом смысле — не столько «золотая рыбка» с её тремя секундами памяти, сколько обаятельный дедушка с прогрессирующим Альцгеймером: искренне рад вам, охотно рассказывает истории, вот только каждый раз новые, а кто вы такой — уже забыл к концу фразы. На демо-ролике это даже трогательно. В реальной игре — катастрофа: экономика, квесты и лор рассыпаются за пару диалогов.

Лечение, увы, не в том, чтобы модель «постаралась запомнить». Нужен способ **совать ей нужную шпаргалку прямо под нос в момент ответа** — и только релевантную, потому что впихнуть в промпт весь лор игры не выйдет (об ограничении контекста — и о том, почему память у нашего героя действительно короткая, — в разделе 7).

### Решение: retrieval прямо в движке

Классический для мира LLM приём — **RAG** (retrieval-augmented generation, «генерация с подтягиванием фактов»). Идея простая, аналогия ещё проще:

> Перед тем как ответить, NPC достаёт нужную шпаргалку и говорит с опорой на неё, а не по памяти.

У каждого NPC есть своя **база знаний**. Она грузится из JSON рядом с персонажем:

```
Resources/NPCs/<ИмяNPC>/emb/knowledge_base.json
```

Но здесь есть нюанс, которого нет в «учебном» RAG. В нашей базе хранятся не абзацы текста, а **набор триггеров** — имя функции и набор параметров. Вот как это выглядит для торговца:

```json
[
  { "signature": "SellItem | item: pistol",
    "action": { "name": "SellItem", "parameters": { "item": "pistol" } } },

  { "signature": "SellItem | item: shotgun",
    "action": { "name": "SellItem", "parameters": { "item": "shotgun" } } },

  { "signature": "SellItem | item: rocket_launcher",
    "action": { "name": "SellItem", "parameters": { "item": "rocket_launcher" } } }
]
```

То есть каждая запись — это заранее «разложенная» тема запроса: с чем игрок может прийти. Но, забегая вперёд, оговоримся сразу: **эта запись не назначает NPC действие.** Она нужна, чтобы понять, *о чём вообще речь*, и подтянуть релевантный контекст. Финальное действие всегда выберет сама модель (об этом — раздел 4).

<!-- КАНДИДАТ ПОД СПОЙЛЕР -->
> 💡 *Что такое эмбеддинги и зачем они нужны (для тех, кто не в теме)*
>
> *Компьютер не понимает смысл слов — он понимает числа. **Эмбеддинг** — это способ превратить кусочек текста в набор чисел (вектор) так, чтобы близкие по смыслу фразы получали близкие наборы чисел. «Продай дробовик», «беру помповое» и «дай ту двустволку» по буквам совсем разные, но по смыслу — почти одно и то же, поэтому их векторы окажутся рядом в пространстве.*
>
> *Наивная альтернатива — искать по ключевым словам — тут же ломается: игрок скажет «двустволка», а в базе записано «shotgun», и поиск по словам ничего не найдёт. Эмбеддинги же сравнивают **по смыслу**, а не по написанию. Мы заранее считаем векторы для всех записей базы знаний, а в момент запроса считаем вектор фразы игрока и находим ближайшие к нему записи — это и есть «семантический поиск».*
>
> *Считает эти векторы отдельная небольшая модель-эмбеддер (не та, что ведёт диалог). Для нас это просто чёрный ящик «текст → вектор»; всё, что нужно знать, — близкие по смыслу тексты дают близкие векторы.*

Поиск устроен так:

```
     фраза игрока                     ┌─────────────────────────┐
  «продай-ка мне дробовик» ─────────▶ │  эмбеддинг запроса       │
                                      └────────────┬────────────┘
                                                   │ вектор
                                                   ▼
   ┌──────────────────────────────────────────────────────────┐
   │            База знаний NPC (векторный индекс)              │
   │   SellItem | item: pistol       ──▶ запись                 │
   │   SellItem | item: shotgun      ──▶ запись   ← ближайшая   │
   │   SellItem | item: sniper_rifle ──▶ запись     (top-K)     │
   └────────────────────────────┬─────────────────────────────┘
                                 │ индексы + score
                                 ▼
              ближайшая запись → какой DataGetter вызвать
                    (тема: «продажа дробовика»)
```

Технически это делает подсистема эмбеддингов плагина: база строится из «сигнатур» записей (`UpdateKbAsync`), а на каждый запрос игрока выполняется семантический поиск (`SearchInKnowledgeBaseAsync`), возвращающий индексы ближайших записей и их оценки близости.

### Запись → DataGetter → контекст

Дальше — самое интересное. У каждой записи есть имя (например, `SellItem`), и этому имени соответствует свой **DataGetter** — объект-«поставщик контекста». Найдя по эмбеддингу ближайшую запись, мы вызываем привязанный к ней DataGetter, и он подтягивает ровно тот контекст, который нужен, чтобы ответить на запрос этой темы:

```
   ближайшая запись                 DataGetter записи             контекст в промпт
   тема: продажа дробовика ────────▶ (свой на каждую тему) ──────▶ "дробовик: 0 шт (нет),
                                     GetNpcState / GetUserState      цена 300, у игрока 250"
```

В коде это связка двух вещей:

- в описании NPC каждое действие (`FNpcActionTemplate`) несёт **и обработчик действия, и свой DataGetter**;
- по имени из сигнатуры нужный поставщик достаётся методом `GetDataGetterByName`, а базовый класс всех таких поставщиков — `UKnowledgeBaseDataGetterBase` (два метода: `GetNpcState` и `GetUserState`).

Иными словами, база знаний решает не «что сделать», а «какой контекст достать». Эмбеддинги отвечают на вопрос *«про что вообще запрос»*, DataGetter — на вопрос *«что модель должна знать, чтобы ответить по этой теме»*. А уже с этим контекстом модель сама решает, что делать.

> **Важно: базу знаний не пишут руками.** Файл `knowledge_base.json` со всеми триггерами и их сигнатурами **генерируется автоматически** на основе описания NPC в его DataAsset. Дизайнер описывает персонажа и его возможности в редакторе — а набор триггеров, их формулировки и эмбеддинги собирает отдельный пайплайн. Это, по сути, маленький MLOps-конвейер, и вместе с обучением LoRA-адаптеров под конкретного NPC он тянет на отдельную статью — так что подробно разберём его в **следующей части**. Здесь важно лишь запомнить: база знаний — это *производная* от описания NPC, а не ручная работа.

### Зачем так, а не «пусть модель сама всё знает»

Игрок может сформулировать одно и то же десятком способов: «продай дробовик», «беру помповое», «дай вон ту двустволку». Задача эмбеддингов — **не решить за модель, что делать**, а надёжно понять, *про какой товар вообще речь*, и подтянуть по нему живые факты: сколько его на складе, почём, хватает ли игроку денег.

И вот тут — важный момент, который часто упускают. Разделение труда получается такое:

- **База знаний** отвечает на вопрос *«о чём запрос»* и достаёт факты.
- **Модель** на основе этих фактов решает, *что делать* — и её выбор ограничен грамматикой (раздел 4).

Обратите внимание на пример в схеме выше: DataGetter вернул «дробовик: 0 шт (нет в наличии)». Игрок просил именно продать — но модель, увидев контекст, выберет не `SellItem`, а `OutOfStock`. Если бы у игрока не хватало денег — `NotEnoughGoldToBuy`. То есть **одна и та же тема запроса приводит к разным действиям** в зависимости от контекста, который принёс DataGetter. Именно поэтому эмбеддинги не должны и не могут назначать действие — они лишь готовят почву, а решение остаётся за моделью.

Почему при этом мелкая локальная модель всё равно иногда ошибается даже с хорошим контекстом — честно разберём в разделе 7.

### Живое состояние: весь контекст идёт через DataGetter

Ключевой архитектурный принцип: **модель получает контекст только через DataGetter — другого канала нет.** Что спросил игрок и что модели про этот запрос нужно знать — вот и весь вход. Состояние приходит двумя каналами (это методы `GetUserState` и `GetNpcState`):

```
   ┌─────────── что спросил игрок ──────────┐
   │  request_of_user: "а дробовик есть?"    │
   ├─────────── состояние игрока ───────────┤
   │  state_of_user:   "ранен, денег 250"    │  ← DataGetter (GetUserState)
   ├─────────── состояние NPC / мира ───────┤
   │  state_of_npc:    "дробовик: 12 шт,     │  ← DataGetter (GetNpcState)
   │                    цена 300"             │
   └─────────────────────────────────────────┘
```

И здесь — главное про универсальность. **Откуда DataGetter берёт это состояние — целиком на усмотрение разработчика.** Модели всё равно: она видит только результат. А внутри DataGetter может тянуть данные откуда угодно:

- **из игровой логики напрямую** — так сделано сейчас: getter спрашивает у ViewModel инвентаря наличие и цену, у игрока — деньги и состояние;
- **из RAG / внешней базы** — если фактов много и их надо искать по смыслу;
- **из чего угодно ещё** — БД, сети, скриптов.

Иными словами, DataGetter — это **единая точка входа контекста** и одновременно точка расширения. Хотите поменять источник данных — правите getter, не трогая ни модель, ни промпт, ни остальной пайплайн. Именно поэтому NPC отвечает не абстрактно, а *к месту*: он «видит» игрока и «помнит» свой ассортимент — а как именно он это «вспомнил», решает разработчик.

## 3.2. Характер: эмоции, голос и лицо

Важно сразу оговорить: эмоция NPC — **не случайный декор и не «настроение вообще»**, а именно **реакция на игрока**. Помните `state_of_user` из предыдущего блока? Модель видит, в каком состоянии игрок и как он себя ведёт, — и отвечает соответствующе. Пришёл раненым и еле живым — торговец посочувствует (`Sad`) и, может, скинет цену. Хамит и требует — насупится (`Angry`). Принёс редкий трофей на продажу — удивится и обрадуется (`Surprise` / `Happy`). Тот же самый вопрос от разных игроков (или от одного и того же, но в разном состоянии) вызовет разную реакцию. Это и есть характер: NPC не выдаёт заготовку, а **реагирует на конкретного собеседника здесь и сейчас**.

### Эмоция приходит вместе с ответом

Технически это красиво решено: модель отдаёт **не просто текст, а структурированный ответ**, где эмоция стоит рядом с репликой:

```json
{
  "emotion": "Happy",
  "answer":  "Конечно, вот лучшие топоры в городе!",
  "action":  { "name": "show_items", "parameters": { "category": "оружие" } }
}
```

Разберём поля:

- **`emotion`** — одно из пяти состояний: `Neutral`, `Happy`, `Sad`, `Angry`, `Surprise`. Это колонна «живёт».
- **`answer`** — то, что уйдёт в озвучку.
- **`action`** — то, что изменит игру (это уже колонна «действует», раздел 4).

То, что эмоция, реплика и действие приходят **одним объектом**, — не случайность. Как заставить модель стабильно выдавать именно такой JSON (и что делать, когда она всё же врёт) — центральная тема раздела 4.

### Эмоция → голос → лицо

Дальше поле `emotion` расходится по двум каналам и «оживляет» MetaHuman:

```
                         "emotion": "Happy"
                                │
              ┌─────────────────┴─────────────────┐
              ▼                                     ▼
   ┌──────────────────────────┐        ┌──────────────────────────┐
   │  сэмпл голоса под эмоцию  │        │   мимика MetaHuman        │
   │  (референс для клонир.)   │        │   выражение лица          │
   │  Neutral/Happy/Sad/       │        │                           │
   │  Angry/Surprise           │        └──────────────────────────┘
   └──────────┬───────────────┘
              ▼
   ┌──────────────────────────┐
   │  синтез речи (клонирование│  ← текст `answer` озвучивается
   │  голоса) в реальном времени│     голосом NPC с нужной эмоцией
   └──────────┬───────────────┘
              ▼
   ┌──────────────────────┐
   │  LipSync (ULSS)      │  ← синхронизация губ по синтезированному аудио
   └──────────────────────┘
```

Здесь важный момент: голос **не проигрывается из заготовок**. В DataAsset персонажа хранятся **сэмплы его голоса с разными эмоциями** (нейтральный, радостный, грустный, злой, удивлённый) — но это не готовые реплики, а **референсы для клонирования голоса**. Модель сказала `Happy` — берём радостный сэмпл как образец тембра и эмоции, и **в реальном времени синтезируем именно текст ответа** этим голосом (voice cloning). Так NPC может произнести любую сгенерированную фразу — своим узнаваемым голосом и с нужным настроением, — а не ограничен набором записанных заранее строк. Параллельно включается соответствующая мимика, а липсинк синхронизирует губы уже под получившееся аудио.

### Живость — это ещё и скорость

Один тонкий, но важный для ощущения жизни момент — **латентность**. Если ждать, пока модель допишет весь ответ, синтезирует речь и только потом откроет рот, пауза убивает вживление.

Поэтому ответ обрабатывается **потоком**: как только из генерации набирается законченное предложение, оно сразу уходит в синтез и озвучку, пока модель дописывает следующее. NPC начинает говорить почти сразу — как живой собеседник, а не как форма с кнопкой «отправить».

```
модель:  токен→токен→токен→[. конец предложения] ──▶ TTS ──▶ говорит
                                       └ параллельно продолжает генерировать →
```

## Итог раздела

NPC ожил за счёт трёх вещей:

1. **База знаний = набор тем запросов.** Эмбеддинги определяют, *про что* спросил игрок, а привязанный к теме **DataGetter** подтягивает нужный контекст (состояние NPC и игрока). Действие база знаний не назначает — это решение модели (раздел 4). Сама база генерируется автоматически из описания NPC — подробнее в следующей части.
2. **Эмоция в структурированном ответе** приходит вместе с репликой и действием одним JSON-объектом.
3. **Голос клонируется в реальном времени** из эмоциональных сэмплов NPC, управляет мимикой и липсинком, а потоковая обработка убирает паузу.

Но пока это NPC, который красиво *реагирует*. Чтобы он ещё и *менял игру*, нужен надёжный механизм действий — к нему и переходим.

## Заметки автора (не для публикации)

- Точные имена API: база знаний — `UULlamaKnowledgeBase` (`UllamaKnowledgeBaseMake/AddChunk/Dispose`), асинхронно — `ULlamaKbUpdateAsync` (`UpdateKbAsync`) и `ULlamaKbSearchAsync` (`SearchInKnowledgeBaseAsync`, отдаёт индексы + score).
- Данные базы: `UNpcKnowledgeBase::Init` читает `Resources/NPCs/<Npc>/emb/knowledge_base.json`, поля записи: `signature` → `FKnowledgeBaseRecord.Request`, `action{name, parameters}`. Реальный формат сигнатуры: `"SellItem | item: pistol"` (имя функции + параметры).
- Триггер → DataGetter: в `FNpcActionTemplate` лежат и `ActionHandler`, и `DataGetter`; резолв по имени — `UNPCDataAsset::GetDataGetterByName` / `GetActionByName` (матч по `ActionTemplate.StartsWith(name + "(")`). Базовый класс поставщика — `UKnowledgeBaseDataGetterBase::GetNpcState / GetUserState` (BlueprintNativeEvent, расширяется в BP).
- База знаний генерируется автоматически из DataAsset NPC (MLOps-пайплайн) — тема следующей статьи, вместе с LoRA. В ч.2 не раскрываем.
- Voice cloning: в `UNPCDataAsset.NpcVoices` (`FNpcVoices`) лежат сэмплы-референсы по эмоциям; речь синтезируется в реальном времени по тексту `answer` (не проигрывание заготовок).
- Формат запроса: `FUserRequestData { Context, StateOfUser, RequestOfUser }`; ответа: `FLlmResponseData { Emotion, Answer, Action{Name,Parameters}, Thoughts }` (парсинг — `ResponseFromJsonString`).
- Эмоции: `ENpcEmotion { Neutral, Angry, Happy, Sad, Surprise, None }`; голоса — `FNpcVoices` в `UNPCDataAsset`.
- Стриминг: `ULlamaManager::GetToken` + `ExtractCompleteSentence` (в раздел 3.2 «живость — это скорость»).
- Проверить перед публикацией: используется ли `Thoughts` реально в проде или только для отладки; какой конфиг эмбеддера (`FULlamaKnowledgeBaseConfig`: ModelFilePath, LoraFilePath, QueryPrefix, GpuLayers).
