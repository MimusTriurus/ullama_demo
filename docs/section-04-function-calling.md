# Раздел 4. Действия NPC: Agent function-calling

> Черновик для статьи (часть 2). Проблему (NPC умеет только говорить, но не влиять на мир) и подход обозначили в разделе 1. Здесь — гвоздь всей статьи: как заставить текстовую модель **надёжно управлять игровой логикой**.

---

## Идея

Идея простая:

> Вместе с текстовым ответом модель возвращает **машинно-исполнимую команду** — имя действия и его параметры. Игра находит обработчик по имени и исполняет команду напрямую: списывает деньги, кладёт товар в сделку, обновляет интерфейс.

То есть фраза «продай-ка мне дробовик» не просто получает вежливый ответ, но и **приводит к реальным изменениям в игре**. Заставить модель *говорить* просто (что сгенерировала — то и озвучили), а вот заставить её надёжно *действовать* — нет. Именно здесь начинаются проблемы, за которые все не любят «LLM в проде»:

- Модель может ответить действием, **которого не существует** («выдать скидку 300%»).
- Может назвать **правильное действие с кривыми параметрами** (`item: "дробовик"` вместо `shotgun`).
- Может завернуть команду в **невалидный JSON** — лишняя запятая, болтовня вокруг, markdown-заборчик ```` ``` ````.
- А маленькая локальная модель делает всё это **чаще** больших облачных (почему — честно в разделе 6).

Дальше — как мы гарантируем, что команда всегда валидна и исполнима.

---

## Решение: как достаём надёжную команду

Готового tool-use под нашу локальную модель нет — собираем его сами. Сначала — общая картина, как NPC приходит к действию. Работает он строго по инструкции из **системного промпта**: проанализировать запрос вместе с контекстом (из раздела 2), выбрать самое подходящее действие и подобрать параметры:

```
   system_prompt (из DataAsset): «проанализируй запрос и контекст,
                                  выбери действие, подбери параметры»
   контекст (раздел 2):          запрос + state_of_user + state_of_npc
              │
              ▼
        ┌──────────┐
        │  модель  │  ← принимает решение на основании промпта и контекста
        └────┬─────┘
             ▼
   "action": { "name": "OutOfStock", "parameters": { "item": "shotgun" } }
```

Главное свойство здесь — **одна и та же фраза даёт разное действие в зависимости от контекста.** «Продай дробовик» при пустом складе превратится в `OutOfStock`, при нехватке денег — в `NotEnoughGoldToBuy`, а обычно — в `SellItem`. Никаких `if`-ов — решает модель.

Красивая картинка — но сама по себе модель такой аккуратный объект выдаёт не всегда (вспомните список бед выше). Поэтому надёжность держится на двух вещах разом:

1. **инструкция** — тот самый системный промпт из схемы. Он делает две вещи: задаёт **форму** — вернуть *один объект структуры* `emotion` + `answer` + `action` (из раздела 3), а не свободный текст; и задаёт **правила выбора** — перечисляет все доступные действия и описывает, в каком случае какое вызывать (например, `DoNothing` — когда вопрос вообще не по адресу торговца), вместе со строгими требованиями к параметрам каждого. Это *что* и *когда* мы хотим получить.
2. **ограничение** — грамматика на уровне сэмплинга не даёт свернуть с этой формы: **страхует** и от галлюцинаций по содержанию, и от некорректного формата — на выходе гарантированно валидный JSON и ничего кроме него (модель не допишет «Вот держите: {…}» и не сломает кавычки).

Инструкцию мы уже разобрали; самое интересное — второе. Грамматики **GBNF** из `llama.cpp` работают радикально: мы не *просим* модель выдать валидный JSON, мы **запрещаем ей на уровне сэмплинга генерировать что-либо, кроме валидного JSON нужной формы**.

Как это работает: на каждом шаге модель выбирает следующий токен из распределения вероятностей. Грамматика на этом же шаге **вычёркивает все токены, которые нарушили бы схему**. Открыли `{` — дальше разрешён только `"emotion"`. После него — только двоеточие. И так далее — в итоге любой сгенерированный ответ гарантированно валиден.

Вот настоящая грамматика нашего торговца:

```gbnf
root      ::= Response
Response  ::= "{" ws "\"emotion\":"  ws emotions "," ws
                  "\"answer\":"   ws string   "," ws
                  "\"action\":"   ws Action ws "}"

Action    ::= "{" ws "\"name\":" ws actions "," ws
                  "\"parameters\":" ws dict "}"

emotions  ::= "Neutral" | "Angry" | "Happy" | "Sad" | "Surprise"

actions   ::= "SellItem" | "NotEnoughGoldToBuy" | "OutOfStock"
            | "ShowItemsByCategory" | "ShowItem" | "DoNothing"
```

Обратите внимание на две строки — `emotions` и `actions`. **Все допустимые эмоции и все допустимые действия перечислены прямо в грамматике.** Модель физически не сможет выдать эмоцию не из пяти или действие, которого у торговца нет: этих вариантов для неё просто не существует на уровне сэмплинга. Не нужно валидировать `"action": "give_discount_300%"` пост-фактум — такой токен-путь заблокирован.

> **Сноска.** Ни грамматику, ни системный промпт, ни базу знаний из раздела 2 не пишут руками — все они собираются из описания NPC в DataAsset. Как устроен этот генератор (целый MLOps-пайплайн) — отдельная тема следующей статьи; здесь достаточно знать: добавить действие = поправить DataAsset.

> Не путать с базой знаний из раздела 2: она отвечает за *контекст* («что показать модели»), грамматика — за *форму и словарь ответа* («что разрешено ответить»). Само действие выбирает модель.

## Исполнение: от намерения к эффекту (ActionHandler → MVVM)

Команду достали. Дальше LLM уже не при делах — за работу берётся игровая логика на стороне Unreal: её задача — **исполнить** действие.

За исполнение отвечает **ActionHandler**: по имени действия из ответа мы находим нужный обработчик и вызываем его.

```
   action: { name: "SellItem", parameters: { item: "shotgun" } }
        │
        ▼
   поиск обработчика по имени действия   ← "SellItem" → его ActionHandler
        │
        ▼
   обработчик (Blueprint) исполняет      ← списать деньги,
   действие                                переложить предмет в сделку
        │
        ▼
   ViewModel инвентаря (MVVM)            ← меняются данные, не UI
        │
        ▼
   UI обновляется автоматически         ← MVVM сам перерисовывает виджеты
```

Два важных момента:

1. **Обработчик — расширяемый.** Базовый обработчик в C++ ничего не делает; вся конкретика (что значит «продать дробовик») пишется в **Blueprint** — там, где дизайнеру удобно. Каждому действию NPC в его DataAsset соответствует свой обработчик.

2. **Действие и слова синхронизированы.** Из одного JSON-ответа `answer` уходит в озвучку, а `action` — в исполнение. Торговец **одновременно** говорит «отличный выбор!» и кладёт дробовик на прилавок.

---

## Итог раздела

**Коротко:** системный промпт и GBNF-грамматика заставляют модель вернуть один валидный объект с действием, а игровая логика Unreal его исполняет.

Мы собрали свой function calling без всякого облака, из двух частей:

1. **системный промпт + GBNF-грамматика** — модель возвращает валидный JSON, а действие извлекается ровно из одного места, поля `action`;
2. **ActionHandler → MVVM** — действие меняет данные, а интерфейс перерисовывается сам.

Теперь у нас есть всё: NPC, который **живёт** (разделы 2–3), и NPC, который **действует** (раздел 4). Осталось увидеть это в работе вместе — на сквозном примере торговца (раздел 5).

- Убран отдельный подблок «Инструкция: …» с повторным листингом JSON-объекта: структура ответа уже дана схемой в «Решении» и разделом 3. Оба `###`-подзаголовка (Инструкция/Ограничение) сняты — грамматика описывается прямо в «Решении» после короткой подводки.
- Из «важных моментов» исполнения убран пункт «Модель не трогает UI напрямую» как частный случай; сам факт «меняются данные, не UI» остался пометкой на диаграмме. Список стал из двух пунктов.
- Действие извлекается ТОЛЬКО из JSON-ответа модели. Механизма inline-триггеров (`[...]`) в статье нет (был выдуман — удалён). `ExtractTrigger` в коде существует, но в пайплайн действий не входит.
- Структурированный ответ: `FLlmResponseData { Emotion, Answer, Action{Name, Parameters}, Thoughts }`, парсинг — `ULlmStructuresHelper::ResponseFromJsonString`. `Thoughts` в статье не показываю. В реальной грамматике торговца поля `thoughts` НЕТ (root → emotion/answer/action) — учтено.
- Грамматика (ПОДТВЕРЖДЕНО по `Resources/NPCs/trader/chat/inference_cfg.json`, поле `grammar_`): `actions ::= SellItem | NotEnoughGoldToBuy | OutOfStock | ShowItemsByCategory | ShowItem | DoNothing`; `emotions ::= Neutral | Angry | Happy | Sad | Surprise`; `parameters` — generic `dict` (значения параметров грамматикой НЕ ограничены).
- Значения параметров (`AllowedParameters_item`, `AllowedParameters_category`) перечислены только в СИСТЕМНОМ ПРОМПТЕ, не в грамматике. То есть имя действия и эмоция — жёстко ограничены; конкретный item — «мягко» (через промпт), что и создаёт почву для ошибок мелких моделей → мост в раздел 6.
- «Правила выбора» в п.1 — ПОДТВЕРЖДЕНО по `system_prompt` в `inference_cfg.json`: блок «Allowed actions and STRICT parameter rules» перечисляет все действия с параметрами; у `DoNothing` есть явный `description` («вопрос совершенно не по теме роли NPC…»), у остальных — правила параметров; финал промпта — «Select the MOST appropriate action». Пример `DoNothing` в тексте взят оттуда.
- Грамматика + системный промпт генерируются из DataAsset NPC (MLOps-пайплайн, ч.3). В конфиге виден `lora_adapter: lora.gguf` — крючок для ч.3.
- Исполнение: `UNPCDataAsset::GetActionByName` (матч `ActionTemplate.StartsWith(name + "(")`) → `UULlamaActionHandlerBase::Execute(ViewModel, ActionName, Params)` (BlueprintNativeEvent; базовая реализация — только лог). Проверить, кто именно вызывает Execute в BP-графе торговца.
- Согласованность с разделом 2: ИСПРАВЛЕНО. Роль KB/эмбеддингов — выбор релевантного DataGetter для сбора контекста; действие выбирает модель (грамматика). Раздел 2 переписан соответственно (подтверждено автором).
