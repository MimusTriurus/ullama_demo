# Раздел 3. Эмоции NPC

> Черновик для статьи (часть 2). В разделе 2 NPC научился *знать* свой мир. Теперь придадим ему **характер** — чтобы он звучал и выглядел по-разному в зависимости от того, что происходит. Действовать (менять игру) он научится в разделе 4.

---

## Проблема: NPC с одним выражением лица

Знать факты — необходимо, но недостаточно. NPC из раздела 2 отвечает правильно, но **одинаково-ровно**: один тон голоса, одно выражение лица на любую реплику. Пришёл игрок раненым и еле живым — дежурная улыбка. Нахамил — та же улыбка. Принёс редкий трофей — снова она.

Собеседник, который реагирует на всё одинаково, ощущается не живым персонажем, а автоответчиком: технически отвечает, а характера — ноль. Значит, нам нужна не «эмоция вообще», а **эмоция как реакция на конкретного игрока здесь и сейчас**.

---

## Решение: эмоция как реакция на ситуацию

Ключевая идея — эмоция не случайный декор и не отдельный запрос к модели, а **вывод из всей ситуации**. Модель выводит её из трёх входов — того же контекста, что использует и для ответа по сути:

```
   ВХОДЫ (что видит модель)                          ВЫХОД
   ┌─────────────────────────────────────┐
   │ тон и суть запроса игрока            │
   │   «дай живо!» / «спасибо, выручил»   │──┐
   ├─────────────────────────────────────┤  │
   │ state_of_user   (раздел 2)           │  │     ┌──────────┐
   │   «ранен, денег в обрез»             │──┼───▶ │  модель  │──▶ "emotion"
   ├─────────────────────────────────────┤  │     └──────────┘        │
   │ state_of_npc    (раздел 2)           │  │                        ▼
   │   «редкий товар, давно не брали»     │──┘              Neutral/Happy/Sad/
   └─────────────────────────────────────┘                 Angry/Surprise
```

Пример: игрок хамит (`тон`), но принёс редкий трофей (`state_of_npc`), да ещё и ранен (`state_of_user`) — модель взвешивает всё вместе и может выдать `Surprise` вместо ожидаемого `Angry`. Эмоция — не таблица «фраза → лицо», а вывод из всей ситуации. Один и тот же вопрос от игрока в разном состоянии даёт разную реакцию.

А наружу эта эмоция выходит **вместе с ответом** — одним структурированным объектом, а не отдельным вызовом:

```json
{
  "emotion": "Happy",
  "answer":  "Конечно, вот лучшие топоры в городе!",
  "action":  { "name": "show_items", "parameters": { "category": "оружие" } }
}
```

- **`emotion`** — одна из пяти (`Neutral`, `Happy`, `Sad`, `Angry`, `Surprise`), выбранная по схеме выше.
- **`answer`** — то, что уйдёт в озвучку.
- **`action`** — то, что изменит игру (об этом — раздел 4).

---

## Эмоция → голос → лицо

Дальше поле `emotion` расходится по двум каналам и «оживляет» MetaHuman:

```
                         "emotion": "Happy"
                                │
              ┌─────────────────┴─────────────────┐
              ▼                                     ▼
   ┌──────────────────────────┐        ┌──────────────────────────┐
   │  сэмпл голоса под эмоцию  │        │   мимика MetaHuman        │
   │  (референс для клонир.)   │        │   выражение лица          │
   │  Neutral/Happy/Sad/       │        │                           │
   │  Angry/Surprise           │        └──────────────────────────┘
   └──────────┬───────────────┘
              ▼
   ┌──────────────────────────┐
   │  синтез речи (клонирование│  ← текст `answer` озвучивается
   │  голоса) в реальном времени│     голосом NPC с нужной эмоцией
   └──────────┬───────────────┘
              ▼
   ┌──────────────────────┐
   │  LipSync (ULSS)      │  ← синхронизация губ по синтезированному аудио
   └──────────────────────┘
```

Здесь важный момент: голос **не проигрывается из заготовок**. В DataAsset персонажа хранятся **сэмплы его голоса с разными эмоциями** — но это не готовые реплики, а **референсы для клонирования**. Модель сказала `Happy` — берём радостный сэмпл как образец тембра и настроения и **в реальном времени синтезируем этим голосом сам текст ответа** (voice cloning). Так NPC может произнести любую сгенерированную фразу — своим узнаваемым голосом и с нужной эмоцией, — а не ограничен набором записанных заранее строк. Параллельно включается мимика, а липсинк подгоняет губы под получившееся аудио.

---

## Итог раздела

Характер NPC складывается из двух вещей:

1. **Эмоция — это реакция на ситуацию**, а не случайный фон: модель выводит её из тона запроса и состояния игрока/NPC (тот же контекст из раздела 2) и отдаёт в структурированном ответе.
2. **Голос клонируется в реальном времени** из эмоциональных сэмплов NPC и управляет мимикой и липсинком.

Теперь NPC помнит (раздел 2) и проявляет характер (раздел 3) — то есть красиво *реагирует*. Но чтобы он ещё и *менял игру*, нужен надёжный механизм действий — к нему и переходим.

## Заметки автора (не для публикации)

- Voice cloning: в `UNPCDataAsset.NpcVoices` (`FNpcVoices`) лежат сэмплы-референсы по эмоциям; речь синтезируется в реальном времени по тексту `answer` (не проигрывание заготовок).
- Эмоции: `ENpcEmotion { Neutral, Angry, Happy, Sad, Surprise, None }`.
- Структура ответа: `FLlmResponseData { Emotion, Answer, Action{Name,Parameters}, Thoughts }` (парсинг — `ResponseFromJsonString`). Поле `Thoughts` в статье не показываю.
- Факт-чек: реально ли эмоция управляет мимикой MetaHuman (в схеме утверждается «мимика») — подтвердить в BP-графе.
- Факт-чек: используется ли `Thoughts` в проде или только для отладки.
