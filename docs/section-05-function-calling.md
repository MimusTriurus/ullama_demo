# Раздел 5. NPC, который действует

> Черновик для статьи (часть 2). Гвоздь всей статьи: как заставить текстовую модель **надёжно управлять игровой логикой**. В разделах 3–4 NPC научился помнить и чувствовать; здесь он научится *менять игру*.

---

## Проблема: болтать легко, действовать — нет

Заставить модель *говорить* — просто: что сгенерировала, то и озвучили. А теперь мы хотим, чтобы фраза «продай-ка мне дробовик» не просто получила вежливый ответ, но и **привела к реальным изменениям в игре**: товар добавлен в сделку, деньги списаны, интерфейс обновлён.

Значит, ответ модели должен представлять собой объект, в котором есть **машинно-исполнимая команда** — имя действия и его параметры, то, что игра сможет исполнить напрямую. И вот тут начинаются проблемы — ровно те, за которые все не любят «LLM в проде»:

- Модель может ответить действием, **которого не существует** («выдать скидку 300%»).
- Может назвать **правильное действие с кривыми параметрами** (`item: "дробовик"` вместо `shotgun`).
- Может завернуть команду в **невалидный JSON** — лишняя запятая, болтовня вокруг, markdown-заборчик ```` ``` ````.
- А маленькая локальная модель делает всё это **чаще** больших облачных (почему — честно в разделе 8).

---

## Решение: как достаём надёжную команду

Готового tool-use под нашу локальную модель нет — собираем его сами. Сначала — общая картина, как NPC приходит к действию. Работает он строго по инструкции из **системного промпта**: проанализировать запрос вместе с контекстом (из раздела 3), выбрать самое подходящее действие и подобрать параметры:

```
   system_prompt (из DataAsset): «проанализируй запрос и контекст,
                                  выбери действие, подбери параметры»
   контекст (раздел 3):          запрос + state_of_user + state_of_npc
              │
              ▼
        ┌──────────┐
        │  модель  │  ← принимает решение на основании промпта и контекста
        └────┬─────┘
             ▼
   "action": { "name": "OutOfStock", "parameters": { "item": "shotgun" } }
```

Отсюда главное свойство: **одна и та же фраза даёт разное действие в зависимости от контекста.** «Продай дробовик» при пустом складе превратится в `OutOfStock`, при нехватке денег — в `NotEnoughGoldToBuy`, а обычно — в `SellItem`. Никаких `if`-ов — решает модель.

Красивая картинка — но сама по себе модель такой аккуратный объект выдаёт не всегда (вспомните список бед выше). Чтобы получить надёжную команду, работают две вещи разом:

1. **инструкция** — в системном промпте модели прямо предписано: вернуть один JSON заданной структуры, выбрать самое подходящее действие и подставить его параметры. Это задаёт, *что* мы хотим получить.
2. **ограничение** — грамматика на уровне сэмплинга не даёт свернуть с этой формы: невалидный JSON, действие или эмоция «из головы» физически невозможны. Это **страхует форму** от галлюцинаций.

Разберём обе. А что делать с готовой командой — уже отдельная история: её исполнение — в следующем блоке.

### Инструкция: ответ — это не текст, а объект

Мы уже видели формат ответа в разделе 4 — теперь смотрим на него глазами «действий»:

```json
{
  "emotion": "Happy",
  "answer":  "Конечно, отличный выбор!",
  "action":  { "name": "SellItem", "parameters": { "item": "shotgun" } }
}
```

Поле `action` — и есть наша команда: `name` (какую функцию вызвать) и `parameters` (с чем). Остальные поля разобраны в разделе 4; здесь нас интересует именно `action`.

Но одного *желания* получить такой JSON мало — модель, предоставленная сама себе, обязательно однажды добавит «Вот держите: {…}» или сломает кавычки. Нужно её **принудить**.

### Ограничение: GBNF-грамматика, при которой модель физически не может ответить неправильно

Здесь работает мощная возможность `llama.cpp` — **грамматики GBNF**. Идея радикальная: мы не *просим* модель выдать валидный JSON, мы **запрещаем ей на уровне сэмплинга генерировать что-либо, кроме валидного JSON нужной формы**.

Как это работает: на каждом шаге модель выбирает следующий токен из распределения вероятностей. Грамматика на этом же шаге **вычёркивает все токены, которые нарушили бы схему**. Открыли `{` — дальше разрешён только `"emotion"`. После него — только двоеточие. И так далее — в итоге любой сгенерированный ответ гарантированно валиден.

Вот настоящая грамматика нашего торговца (единственный листинг в статье — обещаю), слегка почищенная от экранирования ради читаемости:

```gbnf
root      ::= Response
Response  ::= "{" ws "\"emotion\":"  ws emotions "," ws
                  "\"answer\":"   ws string   "," ws
                  "\"action\":"   ws Action ws "}"

Action    ::= "{" ws "\"name\":" ws actions "," ws
                  "\"parameters\":" ws dict "}"

emotions  ::= "Neutral" | "Angry" | "Happy" | "Sad" | "Surprise"

actions   ::= "SellItem" | "NotEnoughGoldToBuy" | "OutOfStock"
            | "ShowItemsByCategory" | "ShowItem" | "DoNothing"
```

Обратите внимание на две строки — `emotions` и `actions`. **Все допустимые эмоции и все допустимые действия перечислены прямо в грамматике.** Модель физически не сможет выдать эмоцию не из пяти или действие, которого у торговца нет: этих вариантов для неё просто не существует на уровне сэмплинга. Не нужно валидировать `"action": "give_discount_300%"` пост-фактум — такой токен-путь заблокирован.

> **Сноска.** Ни грамматику, ни системный промпт, ни базу знаний из раздела 3 не пишут руками — все они собираются из описания NPC в DataAsset. Как устроен этот генератор (целый MLOps-пайплайн) — отдельная тема следующей статьи; здесь достаточно знать: добавить действие = поправить DataAsset.

> Важно не путать с базой знаний из раздела 3: **выбор действия к RAG отношения не имеет.** Действие модель выбирает сама, а грамматика лишь ограничивает её выбор заранее известным перечнем. База знаний и DataGetter'ы отвечают за *контекст* («что показать модели»), грамматика — за *форму и словарь ответа* («что модели разрешено ответить»).

## Исполнение: от намерения к эффекту (ActionHandler → MVVM)

Команду достали. Осталось её **исполнить** — и вот тут вступает архитектура Unreal.

За исполнение отвечает **ActionHandler**: по имени действия из ответа мы находим нужный обработчик и вызываем его.

```
   action: { name: "SellItem", parameters: { item: "shotgun" } }
        │
        ▼
   GetActionByName("SellItem")        ← ищем обработчик по имени
        │
        ▼
   ActionHandler.Execute(ViewModel, "SellItem", { item: "shotgun" })
        │
        ▼
   ViewModel инвентаря               ← меняем данные: списать деньги,
   (MVVM)                              переложить предмет в сделку
        │
        ▼
   UI обновляется автоматически      ← MVVM сам перерисовывает виджеты
```

Три важных момента:

1. **Обработчик — расширяемый.** Базовый `Execute` в C++ ничего не делает; вся конкретика (что значит «продать дробовик») пишется в **Blueprint** — там, где дизайнеру удобно. Каждому действию NPC в его DataAsset соответствует свой обработчик.

2. **Модель не трогает UI напрямую.** Она меняет **ViewModel** — данные. А перерисовка интерфейса — забота **MVVM** (Model-View-ViewModel): виджеты подписаны на данные и обновляются сами. Это чисто и безопасно: LLM влияет на *состояние*, а не на *пиксели*.

3. **Действие и слова синхронизированы.** Из одного JSON-ответа `answer` уходит в озвучку, а `action` — в исполнение. Торговец **одновременно** говорит «отличный выбор!» и кладёт дробовик на прилавок.

## Итог раздела

Мы собрали свой function calling из двух частей, не завися ни от какого облака:

1. **Грамматика GBNF** — гарантирует, что ответ всегда валиден по форме, а действие и эмоция — всегда из заранее известного перечня. И грамматика, и системный промпт генерируются из описания NPC в DataAsset.
2. **ActionHandler → MVVM** — исполняет действие из JSON, меняя данные, а не интерфейс напрямую; интерфейс перерисовывается сам.

Действие при этом извлекается ровно из одного места — из поля `action` ответа модели.

Теперь у нас есть всё: NPC, который **живёт** (разделы 3–4), и NPC, который **действует** (раздел 5). Осталось увидеть это в работе вместе — на сквозном примере торговца (раздел 6).

## Заметки автора (не для публикации)

- Действие извлекается ТОЛЬКО из JSON-ответа модели. Механизма inline-триггеров (`[...]`) в статье нет (был выдуман — удалён). `ExtractTrigger` в коде существует, но в пайплайн действий не входит.
- Структурированный ответ: `FLlmResponseData { Emotion, Answer, Action{Name, Parameters}, Thoughts }`, парсинг — `ULlmStructuresHelper::ResponseFromJsonString`. `Thoughts` в статье не показываю. В реальной грамматике торговца поля `thoughts` НЕТ (root → emotion/answer/action) — учтено.
- Грамматика (ПОДТВЕРЖДЕНО по `Resources/NPCs/trader/chat/inference_cfg.json`, поле `grammar_`): `actions ::= SellItem | NotEnoughGoldToBuy | OutOfStock | ShowItemsByCategory | ShowItem | DoNothing`; `emotions ::= Neutral | Angry | Happy | Sad | Surprise`; `parameters` — generic `dict` (значения параметров грамматикой НЕ ограничены).
- Значения параметров (`AllowedParameters_item`, `AllowedParameters_category`) перечислены только в СИСТЕМНОМ ПРОМПТЕ, не в грамматике. То есть имя действия и эмоция — жёстко ограничены; конкретный item — «мягко» (через промпт), что и создаёт почву для ошибок мелких моделей → мост в раздел 8.
- Грамматика + системный промпт генерируются из DataAsset NPC (MLOps-пайплайн, ч.3). В конфиге виден `lora_adapter: lora.gguf` — крючок для ч.3.
- Исполнение: `UNPCDataAsset::GetActionByName` (матч `ActionTemplate.StartsWith(name + "(")`) → `UULlamaActionHandlerBase::Execute(ViewModel, ActionName, Params)` (BlueprintNativeEvent; базовая реализация — только лог). Проверить, кто именно вызывает Execute в BP-графе торговца.
- Согласованность с разделом 3: ИСПРАВЛЕНО. Роль KB/эмбеддингов — выбор релевантного DataGetter для сбора контекста; действие выбирает модель (грамматика). Раздел 3 переписан соответственно (подтверждено автором).
- Уточнить: `AskWithContext` в C++ закомментирован — как реально прокидывается контекст (`state_of_user/npc`)? Судя по конфигу — через системный промпт + `Ask`.
