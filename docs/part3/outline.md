## Предлагаемая структура

Конвенции те же, что в части 2: нумерованные разделы, «Идея → реализация на абстракциях», мало листингов, много схем, торговец как единственный пример, `Коротко:` в конце разделов 2–7.

### 0. Анонс (до ката)
Напоминание проблемы из части 2 одной строкой + главная цифра: 65.7% → 1.7%. Один абзац, одна мысль: «адаптер под NPC делается из того же DataAsset, без ручной разметки».

### 1. Общая картина
- Два Prefect-флоу: генерация датасета и обучение. Вход — коммит Unreal-проекта + имя NPC. Выход — `lora.gguf` ×2, `knowledge_base.json`, `inference_cfg.json`, отчёт.
- **Схема (mermaid):** DataAsset → экспорт → датасет → два обучения → валидация → артефакты → обратно в `Resources/NPCs/<npc>/`.
- Стек в одну строку: Prefect 3, Ollama (генерация), transformers + PEFT + TRL (LLM), sentence-transformers (эмбеддинги), llama.cpp (конвертация), MinIO (артефакты), `ullama_python` (валидация на движке игры).
- Что на входе буквально: `description.json` — тот же JSON, что `UNPCDataRegistry::GetNpcDataJson` отдаёт игре. Экспорт делает UE-коммандлет на python (`-run=pythonscript`).

### 2. Датасет из DataAsset
Идея: ни одной реплики не написано руками.
- **Шаблоны действий** — единственный листинг раздела: одна запись `ActionData` с `ActionTemplate`, `RequestTemplate`, `UsrStateTemplate`, `NpcStateTemplate`, `Parameters`. Операторы расширенной Jinja: `{{ item[] }}` (цикл), `{{ item_it }}`, `{{ rand_range() }}`, `{{ join() }}`, `{{ Parameters[key] }}`.
- Декартово произведение параметров × **50 ролей игрока** (`user_roles.json`: Rookie Survivor, Gang Leader, Field Medic… со стилем речи) × N перефразов от LLM. Размер подбирается решателем `roles × queries × combos × actions ≈ target`.
- **Три прохода LLM** (схема): (1) перефразы запроса под роль, (2) ответ NPC с эмоцией под уже известное действие, (3) опционально — описание намерения для промпта. Везде маленькие локальные модели через Ollama (qwen3 4b / 8b).
- **Негативы:** `DoNothing` генерируется отдельным «вредительским» промптом — просьбы, на которые торговец ответить не может.
- **Один пример сквозь стадии:** запись `SellItem(pistol)` от шаблона → запрос Rookie Survivor → ответ «Sure! That pistol is just what you need» → chat-формат `messages[]`. Показать как таблицу или схему, не как 4 листинга.
- Стратификация train/val по ключу `action + параметры`, 10% на валидацию. Итог для торговца: ~1000 сырых на действие → 5 529 train / 584 val.
- `Коротко:` разметка из шаблона, текст от LLM, поэтому метки без шума.

### 3. Всё остальное тоже собирается из DataAsset
Закрывает обещание из части 2 («как устроен этот генератор»).
- System prompt (два варианта: chat и tool-calling), GBNF-грамматика, конфиг инференса с семплингом — всё из одного шага.
- База знаний: дедупликация по `(action, params)` → 53 сигнатуры вида `SellItem | item: shotgun`. Почему `NotEnoughGoldToBuy`, `OutOfStock`, `DoNothing` в базу не попадают: это решения LLM по контексту, а не намерения игрока (прямая связь с врезкой про поле `action` в разделе 2 части 2).
- Короткий раздел, в основном схема «один DataAsset → шесть артефактов».

### 4. Обучение адаптера LLM
- QLoRA: база в 4-bit nf4, адаптер в bf16 — иначе на 16 ГБ не влезает вместе с остальным.
- Loss только на ответе ассистента (completion-only) — промпт в 1 700 токенов не должен учиться.
- Гиперпараметры таблицей: r=16, α=32, lr 1e-4, cosine + warmup 5%, 2 эпохи, batch 2 × grad acc 4, early stopping по eval loss, eval каждые 200 шагов. Для 2B: 1 384 шага, eval loss 0.224 → 0.165.
- Конвертация: `convert_hf_to_gguf.py` для базы (один раз, f16) и `convert_lora_to_gguf.py` для адаптера → `lora.gguf` ~21 МБ. Именно этот файл идёт в `FULlamaInferenceConfig.LoraAdapterFilePath`.
- `Коротко:` на той же карте, где игра; адаптер — 21 МБ.

### 5. Обучение адаптера эмбеддингов
Самый неожиданный для читателя раздел — обычно RAG «просто работает».
- Зачем: базовый bge-base промахивается на `ShowItemsByCategory` в 17.5% случаев — путает «покажи медикаменты» и «продай аптечку».
- Датасет пар CoSENT: запрос ↔ сигнатура, score 1.0 (своё действие и параметры), 0.5 (то же действие, другие параметры), 0.0 (другое действие). 13 712 пар.
- **Грабля, ставшая решением:** первый режим `user_request` (пара запрос ↔ другой запрос) наследовал шум из генерации. Перешли на `action_signature`: второй элемент пары — каноническая строка, та же, что лежит в базе знаний. Обучение и поиск видят одинаковые строки.
- Лучший чекпойнт выбирается по `accuracy@1` на retrieval, а не по loss: loss плохо предсказывает top-k.
- `Коротко:` 21.6% → 1.4%.

### 6. Валидация на том же движке, что и игра
- `ullama_python` — биндинги к тем же DLL, что в плагине (`ullama.dll`, `ggml-cuda.dll`). Та же грамматика, тот же семплинг, тот же `reset_history`. Цифры означают то, что увидит игрок, а не то, что показал бы HF-пайплайн.
- Четыре метрики: JSON parse, JSON structure, action, args. Таблица 2B base vs LoRA + график по действиям (есть готовый PNG).
- Сравнение с 4B в одном абзаце: база лучше (39%), после LoRA 0.2% — но часть 2 объяснила, почему 4B в игру не идёт.
- Эмбеддинги: 292 запроса, порог косинуса 0.75, top-k.
- Замыкание сюжета: JSON fails = 0 — грамматика из части 2 держит форму, LoRA чинит смысл. Ровно то разделение, что было обещано.

### 7. Версионирование и доставка
- Путь артефакта говорит сам за себя: `<unreal_commit>/<npc>/<flow_run_id>/training/lora/<base_model>/<dataset>/<hash_гиперпараметров>/`.
- `manifest.json` тянется через все шаги и накапливает: коммит Unreal, коммит пайплайна, размеры датасета, гиперпараметры, пути gguf, метрики. По любому `lora.gguf` в игре можно восстановить, из чего он сделан.
- MinIO (S3) + Prefect artifacts (ссылка, markdown-отчёт, графики) — отчёт виден в UI флоу.
- **Честно про ручное:** в игру файлы пока копируются руками в `Resources/NPCs/trader/{chat,emb}/`; триггер «коммит DataAsset → очередь Prefect» остался в плане.

### 8. Грабли
Короткие, по одному абзацу, как в части 2.
- **История диалога ломает адаптер.** С `reset_history=false` LoRA-модель 4B: 0.2% → 39.8% ошибок, база при этом *лучше* (12%). Обучали на одиночных ходах — валидировать и запускать надо так же. Поэтому в конфиге `reset_history: true`.
- Шум разметки в парах эмбеддингов (см. раздел 5).
- Loss ≠ retrieval accuracy — выбор чекпойнта.
- Расписание LR: 128 эпох «с запасом» + early stopping = весь прогон в warmup, cosine не включился. Перешли на фиксированные `warmup_steps`.
- `trl ≥ 1.0` убрал completion-only collator — пришлось написать свой.
- Инициализация двух llama.cpp-воркеров на одной модели роняет CUDA-бэкенд — очередь под мьютексом (вырезано из части 2, здесь к месту).

### 9. Итог трилогии и что дальше
- Трилогия в три строки: говорящая голова → персонаж с памятью, эмоциями и действиями → персонаж, которого можно «собрать» из DataAsset вместе с его мозгами.
- Что дальше, без обещаний: триггер из git, второй NPC как проверка общности, игра тянет артефакты из S3 сама, квантование базы (q4_k_m уже есть в конвертере).
