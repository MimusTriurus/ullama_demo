# Статья, часть 2 — рабочий план

**Тема:** от «говорящей головы» (PoC из части 1) к живому и полезному NPC.
**Часть 1:** https://habr.com/ru/articles/807561/ (PoC: UE 5.3, Vosk + Mistral 7B + Piper + Oculus LipSync + MetaHuman).

## Параметры (согласовано)

- **Гвоздь двойной:** NPC, который *действует* (function calling) + NPC, который *живёт* (RAG + эмоции).
- **Формат:** мало кода, много схем. Единственный уместный листинг — формат действий / GBNF.
- **Аудитория:** смешанная (как ч.1) — бережно объясняем термины и со стороны LLM, и со стороны UE.
- **Сквозной пример:** один — NPC-торговец.

## Сквозная идея

> В части 1 персонаж научился *говорить*. В части 2 он научился **помнить, чувствовать и действовать** — перестал быть «говорящей головой» и стал участником игры.

Две несущие колонны:
- **Живой** → RAG (намерения в базе + живые факты из игры) + эмоции (голос / мимика).
- **Полезный** → function calling (влияет на игровой мир).

## Арка трилогии (важно держать в голове)

Финал ч.2 (раздел «грабли») готовит почву для ч.3:

> Маленькие модели ошибаются по смыслу (грамматика чинит форму, но не интеллект) → в части 3 автоматически дообучаем **LoRA-адаптер под конкретного NPC**, опираясь на его описание в DataAsset.
>
> Проблему длины контекста / короткой памяти диалога в статью НЕ включаем — по решению автора это отдельная тема за рамками ч.2.

Крючки, которые уже есть в коде и их стоит «подсветить» заранее:
- `FULlamaInferenceConfig.LoraAdapterFilePath` — слот под адаптер уже заложен.
- Data-driven описание NPC (`UNPCDataAsset`) — будущий источник обучающей выборки.

### 1. Общая картина — `docs/parts/section-01-overview.md`
- Подпункты без нумерации: «Что не так было с PoC» → «Что мы с этим сделали» → «Схема работы» → «На чём это работает» → «Почему игра при этом не встаёт» → «Что LLM получает и что отдаёт».
- Что не так было с PoC — **три** боли: NPC статичен (пример «плюмбус»), не влияет на мир («продай пистолет»), эмоционально плоский.
- Что мы с этим сделали — три именованных компонента **в порядке разделов**: `Agent knowledge base` (2), `Expressive Agent` (3), `Agent function-calling` (4), у каждого — номер раздела в скобках. Таблицы «боль → решение → раздел» нет.
- Схема работы — полный пайплайн (STT → RAG → LLM → эмоция/действие → TTS/LipSync/MVVM) с разметкой ◇ каркас / ● сменное (из DataAsset). Выполнена в **mermaid** (`flowchart TD`); ◇/● продублированы значками и цветом. Стрелки вокруг LLM подписаны именами полей контракта. Архитектура и масштабируемость нанесены прямо на эту схему. Там же врезка «Что такое DataAsset».
- На чём это работает — четыре плагина каркаса со ссылками на Fab, модели внутри своих плагинов (Qwen3.5 2B fp16 + Qwen3-Embedding в ULlama, Qwen-STT в SRS, Qwen-TTS в SGS), железо RTX 5070 Ti 16 ГБ, задержка ~1.5 с до первого звука. Плюс объяснение, почему модель именно 2B — это заранее мотивирует раздел 6.
- Почему игра при этом не встаёт — инференс в пуле потоков, стриминг по предложениям, реестр моделей со счётчиком ссылок, врезка про грабли с CUDA-бэкендом. Закрывает главное возражение UE-читателя.
- Что LLM получает и что отдаёт — **контракт объявляется здесь один раз**: вход (`request_of_user` / `state_of_user` / `state_of_npc`) и выход (`emotion` / `answer` / `action`) в json, маршруты полей, ссылка вперёд на грамматику. Разделы 2–4 на него только ссылаются и НЕ переобъявляют.

### 2. NPC знает: Agent knowledge base — `docs/parts/section-02-knowledge.md`
- Заголовки 2–4 — глагольная тройка **NPC знает / NPC чувствует / NPC действует**, она же расплачивается в финале раздела 4 («знает — чувствует — действует»). Вариант «Память NPC» отвергнут: памяти (истории диалога) в разделе нет, история по умолчанию сбрасывается на каждый запрос, а тема памяти диалога вынесена за рамки части 2.
- Подпункты: «Что на самом деле лежит в базе знаний» → «Как распознаётся намерение игрока» → «Откуда берётся контекст». Опенера `## Идея` нет — заход идёт обычным абзацем.
- Ключевой сдвиг: база хранит **намерения игрока** (intent — то, чего он добивается своим запросом), а НЕ факты о мире. Факты меняются в рантайме, поэтому подтягиваются живьём из игрового состояния.
- Поле `action` в записи базы — **ключ к поставщику контекста, а не исполняемая команда**; про это стоит врезка. Иначе читатель спрашивает, зачем нужна LLM, если действие уже в базе.
- Как распознаётся намерение: эмбеддинги (врезка для новичков) → векторный индекс → семантический поиск по смыслу, а не по словам.
- **Поставщик контекста** намерения отдаёт состояние NPC и состояние игрока; источник данных — на выбор разработчика.
- Формат промпта здесь НЕ показываем — он объявлен в разделе 1, отсюда только ссылка. Роль базы: контекст, НЕ выбор действия (это модель, раздел 4).
- Термин «намерение (intent)» — канонический, синхронизирован с разделом 4. Прежнее «тема»/«триггер» не использовать. **Расхождение с кодом:** в `FKnowledgeBaseRecord` поле называется `Request`, в листинге статьи — `intention`.

### 3. Эмоции NPC: Expressive Agent — `docs/parts/section-03-emotions.md`
- Подпункт один: «Тэг эмоции → голос и мимика». Заход — обычным абзацем.
- Три входа эмоции (тот же контекст, что и для ответа, раздел 2): тон запроса + состояние игрока + состояние NPC. Не таблица «фраза → лицо». Пример держим **внутри трёх полей контракта**: хамит, но ранен и без денег → `Sad` (прежний пример с трофеем не годился — трофея среди входов нет).
- Тэг приходит в объекте из раздела 1; листинг не повторяем, только поле `emotion` и пятёрка значений. Гарантия валидности — раздел 4.
- Тэг эмоции → сэмпл голоса для клонирования + мимика MetaHuman → синтез речи в реальном времени → LipSync (ULSS). Сэмплы в DataAsset — референсы, а не готовые реплики.
- Врезка «Что такое MetaHuman»: лицевой риг, мимика как готовый клип (`Face_Joy`, `Face_Anger`, `Face_Neutral`), липсинк — независимый канал по аудио.

### 4. Действия NPC: Agent function-calling — `docs/parts/section-04-function-calling.md` *(гвоздь)*
- Три блока: «Как это работает» → «Но есть нюанс: system prompt ничего не гарантирует» → «Исполнение: ActionHandler → Unreal GameLogic». Заголовок среднего блока намеренно НЕ называет решение (грамматику) — иначе спойлерит развязку; слово «Проблема» в заголовке не использовать, оно занято разделом 6.
- Опенер: вместе с ответом модель возвращает машинно-исполнимую команду. В system prompt лежат **инструкции** (роль, список действий и правила выбора, требования к параметрам, форма ответа), фактов о мире в нём нет — они приезжают в рантайме.
- Список бед «LLM в проде» (несуществующее действие, кривые параметры, невалидный JSON) как мотивация грамматики.
- GBNF-грамматика страхует форму на уровне сэмплинга и держит **весь контракт**: структуру, тэг эмоции, имя действия. Явно сказано, что **значения параметров она НЕ ограничивает** (`parameters` — свободный словарь), поэтому раздел 4 сам ставит вопрос, на который отвечает раздел 6. Листинг грамматики — единственный листинг такого рода в статье.
- Свойство: одна фраза → разное действие в зависимости от контекста (`OutOfStock` / `NotEnoughGoldToBuy` / `SellItem`), без `if`-ов.
- Исполнение: поиск обработчика по имени действия → Blueprint-обработчик → ViewModel → MVVM сам перерисовывает UI. Имена C++ (`GetActionByName`, `Execute`) в тексте не приводим. Врезка «Что такое Blueprint и ViewModel». **Расхождение с проектом:** в тексте сказано «каждому действию свой обработчик», а в проекте их три на шесть действий (`OutOfStock`, `NotEnoughGoldToBuy`, `DoNothing` мир не меняют).

### 5. Демо: NPC-торговец — `docs/parts/section-05-trader-walkthrough.md` *(кульминация)*
- Видео-центричный: минимум схем, доказательство в роликах. Нумерации подпунктов нет.
- Знакомство + скриншот DataAsset (характер в три строки, таблица шести действий) → базовый диалог, где отрабатываются все шесть → вопрос не по адресу (`DoNothing`) → попытка обмана (уговоры не работают, потому что факты берутся из игры).
- Термин «Core игры» не используем — везде «игровая логика».

### 6. Грабли, и почему нужна часть 3 — `docs/parts/section-06-pitfalls-and-part3.md`
- Нумерации подпунктов нет. Заголовок пока «Проблема» — кандидат на переименование в «Грабли: форма без смысла».
- Главная боль: без LoRA точность низкая. Разведено таблицей «что может пойти не так → чем закрыто»: форму закрывает грамматика гарантированно, четыре смысловые проблемы — ничем.
- Ответ: автоматизированный MLOps-пайплайн (датасет из DataAsset → LoRA → оценка → версионирование) + эмбеддинги. Тизер части 3.
