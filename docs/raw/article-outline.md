# Статья, часть 2 — рабочий план

**Тема:** от «говорящей головы» (PoC из части 1) к живому и полезному NPC.
**Часть 1:** https://habr.com/ru/articles/807561/ (PoC: UE 5.3, Vosk + Mistral 7B + Piper + Oculus LipSync + MetaHuman).

## Параметры (согласовано)

- **Гвоздь двойной:** NPC, который *действует* (function calling) + NPC, который *живёт* (RAG + эмоции).
- **Формат:** мало кода, много схем. Единственный уместный листинг — формат действий / GBNF.
- **Аудитория:** смешанная (как ч.1) — бережно объясняем термины и со стороны LLM, и со стороны UE.
- **Сквозной пример:** один — NPC-торговец.

## Сквозная идея

> В части 1 персонаж научился *говорить*. В части 2 он научился **помнить, чувствовать и действовать** — перестал быть «говорящей головой» и стал участником игры.

Две несущие колонны:
- **Живой** → RAG (намерения в базе + живые факты из игры) + эмоции (голос / мимика).
- **Полезный** → function calling (влияет на игровой мир).

## Арка трилогии (важно держать в голове)

Финал ч.2 (раздел «грабли») готовит почву для ч.3:

> Маленькие модели ошибаются по смыслу (грамматика чинит форму, но не интеллект) → в части 3 автоматически дообучаем **LoRA-адаптер под конкретного NPC**, опираясь на его описание в DataAsset.
>
> Проблему длины контекста / короткой памяти диалога в статью НЕ включаем — по решению автора это отдельная тема за рамками ч.2.

Крючки, которые уже есть в коде и их стоит «подсветить» заранее:
- `FULlamaInferenceConfig.LoraAdapterFilePath` — слот под адаптер уже заложен.
- Data-driven описание NPC (`UNPCDataAsset`) — будущий источник обучающей выборки.

### 1. Общая картина — `docs/parts/section-01-overview.md`
- Подпункты без нумерации (как в разделах 2–4): «Что не так было с PoC» → «Что мы с этим сделали» → «Схема работы».
- Что не так было с PoC — **три** боли: NPC статичен (пример «плюмбус»), не влияет на мир («продай пистолет»), эмоционально плоский.
- Что мы с этим сделали — три именованных компонента: `Agent knowledge base` (RAG), `Agent function-calling`, `Expressive Agent` (тэг эмоции → мимика + голос). Таблицы «боль → решение → раздел» нет — навигацию закрывает финальная фраза «далее разберём каждый компонент».
- Схема работы — полный пайплайн (STT → RAG → LLM → эмоция/действие → TTS/LipSync/MVVM) с разметкой ◇ каркас / ● сменное (из DataAsset). Выполнена в **mermaid** (`flowchart TD`); ◇/● продублированы значками и цветом. Архитектура и масштабируемость нанесены прямо на эту схему — отдельного подпункта и второй схемы нет. Перенесено и сжато из бывшего раздела «архитектура»; детали — в разделах 2–4.

### 2. Память NPC: Agent knowledge base — `docs/parts/section-02-memory.md`
- Опенер `## Идея`: перед отправкой в LLM анализируем запрос, достаём из базы факты игрового мира и добавляем к запросу.
- Ключевой сдвиг: база хранит **намерения игрока** (intent — то, чего он добивается своим запросом), а НЕ факты о мире. Факты меняются в рантайме, поэтому подтягиваются живьём из игрового состояния.
- Как распознаётся намерение: эмбеддинги (врезка для новичков) → векторный индекс → семантический поиск по смыслу, а не по словам.
- **Поставщик контекста** намерения отдаёт состояние NPC и состояние игрока; источник данных — на выбор разработчика.
- Что уходит в промпт (`request_of_user` / `state_of_user` / `state_of_npc`). Роль базы: контекст, НЕ выбор действия (это модель, раздел 4).
- Термин «намерение (intent)» — канонический, синхронизирован с разделом 4. Прежнее «тема»/«триггер» не использовать.

### 3. Эмоции NPC: Expressive Agent — `docs/parts/section-03-emotions.md`
- Опенер `## Идея`: вместе с ответом модель возвращает **тэг эмоции**, выведенный из ситуации.
- Три входа эмоции (тот же контекст, что и для ответа, раздел 2): тон запроса + состояние игрока + состояние NPC. Не таблица «фраза → лицо»; пример «хамит, но принёс трофей» → `Surprise`. Согласовано с разделом 1.
- Тэг приходит в структурированном ответе (emotion/answer/action); гарантия валидности — раздел 4.
- Тэг эмоции → сэмпл голоса для клонирования + мимика MetaHuman → синтез речи в реальном времени → LipSync (ULSS). Сэмплы в DataAsset — референсы, а не готовые реплики.

### 4. Действия NPC: Agent function-calling — `docs/parts/section-04-function-calling.md` *(гвоздь)*
- Нумерованных подпунктов нет — три смысловых блока: `## Идея` → `## Решение` → `## Исполнение`.
- Опенер `## Идея`: вместе с ответом модель возвращает машинно-исполнимую команду (имя действия + параметры). Там же — список бед «LLM в проде» (несуществующее действие, кривые параметры, невалидный JSON) как мотивация грамматики.
- Решение: схема «system_prompt + контекст → модель → action». Надёжность держится на двух вещах — **инструкция** (промпт задаёт и форму ответа, и правила выбора действия) + **ограничение** (GBNF-грамматика страхует форму на уровне сэмплинга). Реальная грамматика из `inference_cfg.json` — единственный листинг статьи.
- Свойство: одна фраза → разное действие в зависимости от контекста (`OutOfStock` / `NotEnoughGoldToBuy` / `SellItem`), без `if`-ов.
- Исполнение: поиск обработчика по имени действия → Blueprint-обработчик → ViewModel → MVVM сам перерисовывает UI. Имена C++ (`GetActionByName`, `Execute`) в тексте не приводим — только в заметках автора.

### 5. Сквозной пример: живой торговец — `docs/parts/section-05-trader-walkthrough.md` *(кульминация)*
- Видео-центричный: минимум схем, доказательство в роликах.
- 5.1 Знакомство + скриншот DataAsset; 5.2 базовый диалог; 5.3 разные исходы (OutOfStock/NotEnoughGold); 5.4 вопрос не по адресу (DoNothing); 5.5 попытка обмана (модель не проведёшь); 5.6 итог.

### 6. Грабли, и почему нужна часть 3 — `docs/parts/section-06-pitfalls-and-part3.md`
- 6.1 Главная боль: без LoRA точность низкая (грамматика чинит форму, не смысл).
- 6.2 Ответ: автоматизированный MLOps-пайплайн (датасет из DataAsset → LoRA → оценка → версионирование) + эмбеддинги. Тизер части 3.
