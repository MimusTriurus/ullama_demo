# 1. Общая картина

***

## Что не так было с PoC

* **NPC статичен** — он ничего не знает об игровом мире и, как следствие, выдумывает факты на ходу. Спросите NPC-торговца, есть ли у него плюмбус, и NPC, глазом не моргнув, выразит готовность его продать и даже назовёт цену.

* **NPC не может влиять на игровой мир**. Нельзя было попросить "продай пистолет, пожалуйста" и получить ствол в инвентарь, потратив при этом деньги.

* **NPC эмоционально плоский**. Один голос, одно выражение лица на любую реплику игрока (какой бы хамской она ни была).

***

## Каждый из недочетов PoC мы закрыли своим механизмом:

* **Agent knowledge base** — база знаний (RAG) для NPC, синхронизированная с игровым миром. NPC анализирует запрос игрока, извлекает из БЗ факты и отвечает игроку в соответствии с ними.

* **Agent function-calling** — NPC анализирует запрос игрока, выбирает действие (из заданного списка) и возвращает его вместе с ответом; игровая логика выполняет действие.

* **Expressive Agent** — NPC анализирует тональность запроса игрока (не хамит ли), состояние игрока (не ранен ли), собственное состояние и вместе с текстовым ответом возвращает тэг эмоции, соответствующий ситуации. Этот тэг определяет, какую анимацию лица (MetaHuman) применить и какой сэмпл голоса использовать для клонирования при преобразовании текста в речь.

Так NPC перестаёт быть просто говорящим болванчиком. Теперь у него будет представление об игровом мире и его динамике, он будет уметь проявлять характер, эмоции и влиять на геймплей.

## Схема работы

```mermaid

    Player["🎤 Игрок<br/>(микрофон)"]
    STT["◇ STT плагин -<br/>речь -> текст"]
    KB["◇ RAG плагин -<br/>База знаний об игровом мире<br/>● факты этого NPC"]
    LLM["Llama.cpp плагин -<br/>локальный инференс (CUDA)<br/> ◇ llm модель +<br/> ● LoRA + ● промпт + ● грамматика"]
    TTS["◇ TTS плагин -<br/>текст -> voice cloning -> речь<br/>● сэмплы голоса NPC"]
    ACT["Эмоции + действие<br/>● ActionHandler (Blueprint)"]
    LS["◇ LipSync плагин -<br/>анимация губ MetaHuman"]
    UI["● Unreal Game State<br/>MVVM инвентаря торговца и т.д. и т.п."]
    OUT(["MetaHuman говорит -<br/>губы, мимика и эмоция синхронно"])

    Player -- голос --> STT
    STT -- "request_of_user" --> LLM
    KB -- "state_of_user + state_of_npc" --> LLM
    LLM -- "answer" --> TTS
    LLM -- "emotion + action" --> ACT
    TTS -- аудио --> LS
    ACT -- изменение состояния --> UI
    LS --> OUT
    ACT -. мимика .-> OUT

    classDef swap fill:#fff3e0,stroke:#d9822b,stroke-width:2px,color:#3b2a12

    class ACT swap

```

> ◇ — **каркас**, один на всех NPC ● — **сменное**, из DataAsset этого NPC

На схеме видно, что есть общая для всех типов NPC часть (◇): распознавание и синтез речи, lip sync для MetaHuman, инференс LLM (базовая модель к тому же грузится в память один раз на всех — десять NPC делят одну, а не тянут десять копий).

Всё, что касается конкретного NPC (●), берётся из его `DataAsset`: описание характера, LoRA-адаптер "специализирующий" LLM под NPC, сэмплы голоса и "мосты" к игровой логике (ActionHandler / DataGetter).

Чтобы добавить нового NPC, достаточно заполнить соответствующие поля в DataAsset. Не надо переписывать движок. **NPC становится контентом, а не кодом.**

И ещё одно, общее для всей схемы: весь этот пайплайн работает **локально** — приватность, никакой сетевой задержки и платы за токены.

## Что LLM получает и что отдаёт

На схеме подписаны стрелки вокруг LLM — это и есть два "контракта" всей системы.

**На входе** — три поля: сам запрос игрока (`request_of_user`) плюс два канала живых фактов из игры, `state_of_user` и `state_of_npc`:

```json
{
  "request_of_user": "покажи, что есть из оружия",
  "state_of_user":   "ранен, денег 250$",
  "state_of_npc":    "дробовик: 12 шт, цена 300$; пистолет: 3 шт, цена 150$"
}
```

Откуда берутся эти факты — раздел 2.

**На выходе** — не свободный текст, а такой же строгий json объект:

```json
{
  "emotion": "Happy",
  "answer":  "Конечно, вот лучшие стволы в городе!",
  "action":  { "name": "ShowItemsByCategory", "parameters": { "category": "weapons" } }
}
```

Дальше каждое поле уходит своим маршрутом: `answer` — в озвучку, `emotion` — в мимику MetaHuman и выбор сэмпла голоса (раздел 3), `action` — в игровую логику (раздел 4).

Причём нарушить этот формат модель физически не может. И структура объекта, и допустимые значения `emotion` и `action` заданы **грамматикой на уровне сэмплинга** — как именно, разберём в разделе 4.
