# Раздел 2. С высоты птичьего полёта

> Черновик для статьи (часть 2). Задача раздела — дать читателю карту целиком, чтобы дальше можно было нырять в детали, не теряя контекст.

---

## 2.1. Что не так было с PoC

В первой части мы собрали работающий прототип: персонаж слышал игрока, отправлял распознанный текст в языковую модель, получал ответ и озвучивал его с движением губ. Это впечатляло на демо — ровно тридцать секунд, пока не начинаешь задавать вопросы:

- NPC **не помнил фактов мира** — он придумывал цены, имена и события на ходу.
- NPC **ничего не делал** — только говорил. Нельзя было попросить «покажи топоры» и увидеть реакцию игры.
- Персонаж был **эмоционально плоским** — один голос, одно выражение лица на любую реплику.
- Всё было **захардкожено** под одного героя — добавить второго значило переписать половину проекта.

Иными словами, у нас была *говорящая голова*. Во второй части мы превращаем её в **участника игры**: того, кто помнит, чувствует и действует.

---

## 2.2. Что мы с этим сделали

На каждую боль — свой ответ. Всё это и есть содержание статьи:

| Боль из 2.1 | Решение | Где в статье |
|---|---|---|
| не помнил фактов мира | **RAG**: контекст под запрос подтягивает DataGetter | раздел 3 |
| был эмоционально плоским | **эмоция в ответе** → голос (клонирование) и мимика | раздел 4 |
| ничего не делал | **function calling**: GBNF-грамматика + ActionHandler → MVVM | раздел 5 |
| был захардкожен | **data-driven NPC**: персонаж описан данными, артефакты генерируются | разделы 2.4–2.5 |

Память (раздел 3) и эмоции (раздел 4) складываются в идею **«NPC, который живёт»**; function calling — это **«NPC, который действует»** (раздел 5). Вместе они собираются в сквозном примере торговца (раздел 6), а держит всё это data-driven архитектура — к ней мы вернёмся в конце этого же раздела (2.4–2.5).

---

## 2.3. Полный конвейер

Прежде чем разбирать по частям — вот весь путь одной реплики игрока, от микрофона до реакции игры.

```
 ┌──────────────┐   голос     ┌──────────────┐   текст запроса
 │    Игрок     │ ──────────▶ │  STT (Qwen)  │ ──────────────┐
 │  (микрофон)  │             │ речь → текст │               │
 └──────────────┘             └──────────────┘               │
                                                             ▼
 ┌──────────────┐                    ┌───────────────────────────────────┐
 │  База знаний │  релевантные       │        ULlamaPlugin (llama.cpp)    │
 │    (RAG)     │ ─── факты ───────▶ │  локальный инференс, стриминг      │
 │  эмбеддинги  │                    │  токенов, CUDA                     │
 └──────────────┘                    └───────┬───────────────────┬───────┘
                                             │ текст ответа       │ эмоция + действие
                                             ▼                    ▼
                              ┌──────────────────────┐  ┌──────────────────────────┐
                              │  SpeechGenSystem TTS │  │  Эмоции + ActionHandler   │
                              │  синтез голоса       │  │  реакция + игровое действие│

                        ┌────────────────┴───────┐               ▼

              ┌──────────────────┐    ┌──────────────┐ │      MVVM UI              │
              │  ULSS / LipSync  │    │ клонирование │ │  инвентарь торговца и т.д. │

              └──────────────────┘    └──────────────┘
                        │
                        ▼
        MetaHuman говорит — с синхронизацией губ, мимикой и эмоцией
```

> **TODO для вёрстки:** перерисовать в нормальную векторную схему (это ASCII-черновик). Выделить цветом две колонны: «живёт» (RAG + эмоции) и «действует» (триггеры + UI).

Коротко: **STT** (Qwen-STT) переводит речь в текст → к запросу подмешивается контекст из **RAG** → **ULlamaPlugin** (`llama.cpp`) генерирует ответ потоком токенов, локально → из ответа берём и текст, и эмоцию, и действие → текст озвучивается (**TTS** с клонированием голоса под эмоцию) и синхронизируется с губами (**LipSync**), а действие меняет игру через **MVVM**.

Ключевая мысль: **всё это работает локально**, без облака и интернета — со всеми плюсами (приватность, отсутствие сетевой задержки и платы за токены) и всеми граблями (о них — в разделе 7).

## 2.4. Как это устроено: четыре слоя

Схема выше — это как система *работает*. Не менее важно, как она *устроена*: в части 1 всё было единым куском кода вокруг одного героя, и любая новая идея тянула за собой правку всего. Во второй части мы развели ответственность по четырём слоям, чтобы каждый можно было менять отдельно:

```
   ┌──────────────────────────────────────────────────────────────┐
   │  4. ДАННЫЕ NPC        DataAsset + Resources/NPCs/<имя>/        │
   │     (кто это, что умеет, как звучит)   ← правит гейм-дизайнер  │
   ├──────────────────────────────────────────────────────────────┤
   │  3. ЛОГИКА NPC        Blueprint: ActionHandler, DataGetter     │
   │     (что делает действие, откуда контекст) ← правит разработчик│
   ├──────────────────────────────────────────────────────────────┤
   │  2. СКЛЕЙКА           игровой C++ модуль (реестр NPC,          │
   │     (общий каркас)     структуры ответа, эмоции)               │
   ├──────────────────────────────────────────────────────────────┤
   │  1. ТЕХНОЛОГИИ        STT (Qwen3-STT), ULlamaPlugin (LLM+RAG), │
   │     (переиспользуемое)  TTS, LipSync                           │
   └──────────────────────────────────────────────────────────────┘
```

Правило простое: **чем выше слой — тем чаще его трогают и тем меньше для этого нужно быть программистом; чем ниже — тем стабильнее и универсальнее.** Два нижних слоя ничего не знают про торговца — те же STT / LLM / TTS / LipSync можно переиспользовать в другом проекте (часть из них и живёт отдельно, на Marketplace). Вся специфика персонажа — наверху: в Blueprint-логике (что делает действие — раздел 5; откуда берётся контекст — раздел 3) и в данных (голос и эмоции — раздел 4). Каждый слой детально разберём в следующих разделах.

## 2.5. Сколько стоит второй NPC

Такое расслоение окупается на главном вопросе роста — «во сколько обойдётся ещё один персонаж». В части 1 — переписать половину проекта. Здесь:

```
   Хочу нового NPC — механика-оружейника
        │
        ├─ 1. Новый DataAsset: имя, характер, действия, голоса   (дизайнер)
        ├─ 2. Прогнать пайплайн → промпт, грамматика, база, LoRA (авто, часть 3)
        ├─ 3. ActionHandler'ы под его действия                    (Blueprint)
        └─ 4. DataGetter'ы под его контекст                       (Blueprint)

   Слои 1–2 (технологии и склейка) НЕ трогаем вообще.
```

Технологический фундамент остаётся нетронутым — меняются только данные и, если у персонажа есть уникальные действия, их обработчики. **NPC становится контентом, а не кодом.** Масштабируется это и по памяти: базовая модель грузится один раз и разделяется между всеми NPC, что её используют, — десять торговцев на одной модели занимают память одной, а не десяти.

А как из одного DataAsset сами собой берутся промпт, грамматика, база знаний и LoRA-адаптер (шаг 2 «авто») — это целиком тема части 3.
