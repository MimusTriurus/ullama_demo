# Раздел 2. С высоты птичьего полёта

> Черновик для статьи (часть 2). Задача раздела — дать читателю карту целиком, чтобы дальше можно было нырять в детали, не теряя контекст.

---

## 2.1. Что не так было с PoC

В первой части мы собрали работающий прототип: персонаж слышал игрока, отправлял распознанный текст в языковую модель, получал ответ и озвучивал его с движением губ. Это впечатляло на демо — ровно тридцать секунд, пока не начинаешь задавать вопросы:

- NPC **не помнил фактов мира** — он придумывал цены, имена и события на ходу.
- NPC **ничего не делал** — только говорил. Нельзя было попросить «покажи топоры» и увидеть реакцию игры.
- Персонаж был **эмоционально плоским** — один голос, одно выражение лица на любую реплику.
- Всё было **захардкожено** под одного героя — добавить второго значило переписать половину проекта.

Иными словами, у нас была *говорящая голова*. Во второй части мы превращаем её в **участника игры**: того, кто помнит, чувствует и действует.

---

## 2.2. Было / стало

| | Часть 1 (PoC) | Часть 2 (эта статья) |
|---|---|---|
| Движок | UE 5.3 | UE 5.7 |
| Устройство | монолитная связка | 3 отдельных плагина |
| Диалог | простой «промпт → ответ» | RAG: ответ с опорой на факты мира |
| Игровая логика | нет, только речь | function calling: LLM управляет игрой |
| Характер | один голос | эмоции → голос → мимика |
| Создание NPC | хардкод | data-driven (Data Asset + JSON) |
| Интерфейс | нет | UI на MVVM, которым управляет NPC |
| Железо | CPU | CPU / GPU (CUDA) |

Правый столбец — это, по сути, оглавление статьи. Дальше мы пройдём по нему, сгруппировав всё вокруг двух идей: **NPC, который живёт** (память + эмоции) и **NPC, который действует** (function calling).

## 2.3. Полный конвейер

Прежде чем разбирать по частям — вот весь путь одной реплики игрока, от микрофона до реакции игры.

```
 ┌──────────────┐   голос     ┌──────────────┐   текст
 │    Игрок     │ ──────────▶ │  STT (Qwen)  │ ──────────▶ ┐
 │  (микрофон)  │             │ речь → текст │             │
 └──────────────┘             └──────────────┘             │
                                                            ▼
                              ┌───────────────────────────────────────────┐
                              │           Сборка промпта                    │
                              │  личность NPC + история + факts из RAG      │
                              └───────────────────────┬─────────────────────┘
        ┌── память ──────────────────────────────────┤
        ▼                                             ▼
 ┌──────────────┐                    ┌───────────────────────────────────┐
 │  База знаний │  релевантные       │        ULlamaPlugin (llama.cpp)    │
 │    (RAG)     │ ─── факты ───────▶ │  локальный инференс, стриминг      │
 │  эмбеддинги  │                    │  токенов, CUDA                     │
 └──────────────┘                    └───────┬───────────────────┬───────┘
                                             │ текст ответа       │ эмоция + триггер
                                             ▼                    ▼
                              ┌──────────────────────┐  ┌──────────────────────────┐
                              │  SpeechGenSystem TTS │  │  Эмоции + ActionHandler   │
                              │  синтез голоса       │  │  реакция + игровое действие│
                              └──────────┬───────────┘  └───────┬──────────────────┘
                                         │ аудио                 │
                        ┌────────────────┴───────┐               ▼

                        │

        MetaHuman говорит — с синхронизацией губ, мимикой и эмоцией
```

Читается схема так:

1. **STT** — голос игрока превращается в текст. В части 1 это был Vosk; во второй версии распознавание построено на **Qwen-STT**.
2. **Сборка промпта** — к запросу подмешиваются личность NPC, недавняя история диалога и — новое во второй части — **релевантные факты из базы знаний** (RAG).
3. **Инференс** — `ULlamaPlugin` поверх `llama.cpp` генерирует ответ **потоком токенов**, локально, при желании на GPU.
4. **Развилка** — из потока мы вытаскиваем не только текст для озвучки, но и **эмоцию** и **триггер-действие**.
5. **Озвучка и лицо** — текст уходит в TTS, аудио — в липсинк; голос и мимика подбираются под эмоцию.
6. **Действие** — триггер исполняется обработчиком и меняет игровое состояние через MVVM (например, инвентарь торговца).

Ключевая мысль: **всё это работает локально**, без облака и интернета — со всеми плюсами (приватность, отсутствие сетевой задержки и платы за токены) и всеми граблями (о них — в разделе 7).

## 2.4. Две колонны, к которым всё сводится

Чтобы не утонуть в компонентах, дальше статья держится за две идеи:

```
        NPC, который ЖИВЁТ                    NPC, который ДЕЙСТВУЕТ
        ─────────────────                    ──────────────────────
        RAG — память фактов                  триггеры-действия (наш function calling)
        эмоции → голос → мимика              GBNF-грамматика для надёжного парсинга
                                             ActionHandler → MVVM → игровой UI
              (раздел 3)                              (раздел 4)
                    └──────────────┬───────────────────┘
                                   ▼
                    Сквозной пример: торговец (раздел 5)
```

- **Раздел 3** — как NPC обрёл память и характер.
- **Раздел 4** — как NPC научился влиять на игру.
- **Раздел 5** — собираем обе колонны в одном примере: живой торговец, который реально торгует.

А то, что держит всю конструкцию вместе — модульная архитектура и data-driven описание NPC, — разберём в разделе 6, ближе к концу: это фундамент, а не витрина.
