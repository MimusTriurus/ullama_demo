# Раздел 2. Память NPC

> Черновик для статьи (часть 2). Первое, что отличает живого NPC от «говорящей головы», — он **знает факты своего мира** и не выдумывает их на ходу. Разберём, как устроена эта память. Характер и эмоции — в разделе 3.

---

## Проблема «золотой рыбки»

Языковая модель сама по себе не знает про ваш мир ровным счётом ничего. Зато врёт с обезоруживающей уверенностью. Спросите торговца, есть ли у него железный топор и почём — и маленькая модель, глазом не моргнув, назовёт цену, которую только что сочинила. Спросите ещё раз через минуту — цена будет другая. И товар, возможно, тоже.

Наш NPC в этом смысле — не столько «золотая рыбка» с её тремя секундами памяти, сколько обаятельный дедушка с прогрессирующим Альцгеймером: искренне рад вам, охотно рассказывает истории, вот только каждый раз новые, а кто вы такой — уже забыл к концу фразы. На демо-ролике это даже трогательно. В реальной игре — катастрофа: экономика, квесты и лор рассыпаются за пару диалогов.

Лечение, увы, не в том, чтобы модель «постаралась запомнить». Нужен способ **совать ей нужную шпаргалку прямо под нос в момент ответа** — и только релевантную, потому что впихнуть в промпт весь лор игры не выйдет — контекст модели ограничен, и кормить её нужно точечно.

---

## Решение: retrieval прямо в движке

Классический для мира LLM приём — **RAG** (retrieval-augmented generation, «генерация с подтягиванием фактов»). Идея простая, аналогия ещё проще:

> Перед тем как ответить, NPC достаёт нужную шпаргалку и говорит с опорой на неё, а не по памяти.

Почему не «пусть модель сама всё знает»? Затем, что она не знает и не запомнит (см. золотую рыбку), а игрок формулирует одно и то же десятком способов — «продай дробовик», «беру помповое», «дай двустволку». Надёжнее не гадать, а найти нужные факты по смыслу и подать их модели готовыми. При этом поиск определяет, *про что* запрос и *что достать*, — но не назначает действие: что делать, модель решает сама (раздел 4).

У каждого NPC есть своя **база знаний**. Она грузится из JSON рядом с персонажем:

```
Resources/NPCs/<ИмяNPC>/emb/knowledge_base.json
```

Но здесь есть нюанс, которого нет в «учебном» RAG. В нашей базе хранятся не абзацы текста, а **набор триггеров** — имя функции и набор параметров. Вот как это выглядит для торговца:

```json
[
  { "signature": "SellItem | item: pistol",
    "action": { "name": "SellItem", "parameters": { "item": "pistol" } } },

  { "signature": "SellItem | item: shotgun",
    "action": { "name": "SellItem", "parameters": { "item": "shotgun" } } },

  { "signature": "SellItem | item: rocket_launcher",
    "action": { "name": "SellItem", "parameters": { "item": "rocket_launcher" } } }
]
```

То есть каждая запись — это заранее «разложенная» тема запроса: с чем игрок может прийти. По ней мы поймём, *о чём* речь, и подтянем нужный контекст (выбор действия, напомню, — не её забота, а модели).

<!-- КАНДИДАТ ПОД СПОЙЛЕР -->
> 💡 *Что такое эмбеддинги и зачем они нужны (для тех, кто не в теме)*
>
> *Компьютер не понимает смысл слов — он понимает числа. **Эмбеддинг** — это способ превратить кусочек текста в набор чисел (вектор) так, чтобы близкие по смыслу фразы получали близкие наборы чисел. «Продай дробовик», «беру помповое» и «дай ту двустволку» по буквам совсем разные, но по смыслу — почти одно и то же, поэтому их векторы окажутся рядом в пространстве.*
>
> *Наивная альтернатива — искать по ключевым словам — тут же ломается: игрок скажет «двустволка», а в базе записано «shotgun», и поиск по словам ничего не найдёт. Эмбеддинги же сравнивают **по смыслу**, а не по написанию. Мы заранее считаем векторы для всех записей базы знаний, а в момент запроса считаем вектор фразы игрока и находим ближайшие к нему записи — это и есть «семантический поиск».*
>
> *Считает эти векторы отдельная небольшая модель-эмбеддер (не та, что ведёт диалог). Для нас это просто чёрный ящик «текст → вектор»; всё, что нужно знать, — близкие по смыслу тексты дают близкие векторы.*

Весь путь от реплики до готового контекста — одной схемой:

```
  фраза игрока              эмбеддинг         ближайшая запись
  «продай дробовик» ──────▶ (вектор) ──────▶ SellItem | item: shotgun
                                              (тема: продажа дробовика)
                                                        │
                                                        ▼
                                          DataGetter этой темы
                                          (GetNpcState / GetUserState)
                                                        │
                                                        ▼
                                    контекст ──▶ в промпт модели
```

Технически: база строится из «сигнатур» записей (`UpdateKbAsync`), поиск по фразе игрока делает `SearchInKnowledgeBaseAsync` (возвращает индексы ближайших записей и score). У каждой записи есть имя (`SellItem`) — по нему находится её **DataGetter** (`GetDataGetterByName`). Все геттеры наследуют `UKnowledgeBaseDataGetterBase` с двумя методами — `GetNpcState` и `GetUserState`; привязка «имя → обработчик + геттер» лежит в `FNpcActionTemplate` описания NPC.

> **Сноска.** Базу знаний не пишут руками: `knowledge_base.json` генерируется из описания NPC в DataAsset — тем же пайплайном, что собирает системный промпт и грамматику (раздел 4). Как устроен этот генератор — отдельная тема следующей статьи; здесь важно лишь, что база — производная от DataAsset.

## Что уходит в промпт

Два канала геттера (`GetUserState` и `GetNpcState`) вместе с самим запросом и образуют весь вход модели:

```
   request_of_user: "а дробовик есть?"
   state_of_user:   "ранен, денег 250"          ← GetUserState
   state_of_npc:    "дробовик: 12 шт, цена 300"  ← GetNpcState
```

Главное здесь — **источник состояния целиком на усмотрение разработчика**: модель видит только результат. Сейчас DataGetter спрашивает игровую логику напрямую (инвентарь, деньги, здоровье), но с тем же контрактом мог бы ходить в RAG, БД или внешний сервис. Поменять источник — значит поправить один getter, не трогая ни модель, ни остальной пайплайн. Поэтому NPC отвечает *к месту* — а как он «вспомнил», решает разработчик.

## Итог раздела

Память NPC держится на трёх вещах:

1. **База знаний = набор тем запросов.** Эмбеддинги определяют, *про что* спросил игрок.
2. **DataGetter** по теме подтягивает нужный контекст (состояние NPC и игрока) — откуда именно, решает разработчик.
3. **Действие база знаний не назначает** — это решение модели (раздел 4). А сама база генерируется автоматически из описания NPC — подробнее в следующей части.

Теперь NPC знает свой мир и отвечает к месту. Но говорит он пока одинаково-ровно. Придать ему характер — эмоции, голос, живое лицо — задача следующего раздела. (А почему модель иногда ошибается даже с хорошим контекстом — честно разберём в разделе 6.)

## Заметки автора (не для публикации)

- Точные имена API: база знаний — `UULlamaKnowledgeBase` (`UllamaKnowledgeBaseMake/AddChunk/Dispose`), асинхронно — `ULlamaKbUpdateAsync` (`UpdateKbAsync`) и `ULlamaKbSearchAsync` (`SearchInKnowledgeBaseAsync`, отдаёт индексы + score).
- Данные базы: `UNpcKnowledgeBase::Init` читает `Resources/NPCs/<Npc>/emb/knowledge_base.json`, поля записи: `signature` → `FKnowledgeBaseRecord.Request`, `action{name, parameters}`. Реальный формат сигнатуры: `"SellItem | item: pistol"` (имя функции + параметры).
- Триггер → DataGetter: в `FNpcActionTemplate` лежат и `ActionHandler`, и `DataGetter`; резолв по имени — `UNPCDataAsset::GetDataGetterByName` / `GetActionByName` (матч по `ActionTemplate.StartsWith(name + "(")`). Базовый класс поставщика — `UKnowledgeBaseDataGetterBase::GetNpcState / GetUserState` (BlueprintNativeEvent, расширяется в BP).
- База знаний генерируется автоматически из DataAsset NPC (MLOps-пайплайн) — тема следующей статьи, вместе с LoRA. В ч.2 не раскрываем.
- Формат запроса: `FUserRequestData { Context, StateOfUser, RequestOfUser }` — отдельного `state_of_npc` в структуре нет; в схеме показан ради читаемости, свериться (вероятно через `Context`).
- Конфиг эмбеддера: `FULlamaKnowledgeBaseConfig` (ModelFilePath, LoraFilePath, QueryPrefix, GpuLayers).
