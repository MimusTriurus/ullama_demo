# Раздел 2. Память NPC: Agent knowledge base

> Черновик для статьи (часть 2). Проблему (NPC выдумывает факты) и подход (RAG) мы обозначили в разделе 1. Здесь — как это устроено: что в базе, как по фразе игрока распознаётся его намерение и откуда берётся актуальное состояние мира.

---

## Идея

Идея простая:

> Перед тем как отправить запрос игрока в LLM, мы анализируем этот запрос, извлекаем из базы знаний NPC факты игрового мира и добавляем их к запросу.

Так модель отвечает, опираясь на реальное состояние игры, а не на выдумку. Дальше разберём это по слоям: что лежит в базе знаний → как находится нужная запись → откуда берётся актуальное состояние мира → что уходит в модель.

---

## База знаний хранит намерения, а не факты

Здесь принципиальное отличие от привычного представления о RAG. Наша база **не хранит знаний о мире** — ни цен, ни остатков, ни лора. В ней лежат только **намерения игрока** — то, чего он добивается от NPC своим запросом (в диалоговых системах это называют *intent*). Каждое намерение — это сигнатура вида «действие + параметры» с привязкой к своему **поставщику контекста**:

```json
[
  { "signature": "SellItem | item: pistol",  "action": { "name": "SellItem",  "parameters": { "item": "pistol" } } },
  { "signature": "SellItem | item: shotgun", "action": { "name": "SellItem",  "parameters": { "item": "shotgun" } } }
]
```

Почему так, а не «сложить в базу все факты»: факты меняются в рантайме (товар купили, деньги потратили, игрока ранили). Хранить их копию в базе — значит гарантированно рассинхронизировать её с игрой. Поэтому база отвечает лишь на вопрос **«чего добивается игрок»**, а сами факты подтягиваются **живьём из игрового состояния** в момент ответа — и всегда актуальны.

> 💡 *Что такое эмбеддинги (для тех, кто не в теме)*
>
> *Компьютер понимает не смысл слов, а числа. **Эмбеддинг** превращает кусочек текста в вектор так, что близкие по смыслу фразы получают близкие векторы. «Продай дробовик», «беру помповое» и «дай двустволку» по буквам разные, а по смыслу — почти одно, поэтому их векторы окажутся рядом. Поиск по ключевым словам тут ломается (в базе «shotgun», а игрок сказал «двустволка»), а семантический — нет. Векторы считает отдельная маленькая модель-эмбеддер (не та, что ведёт диалог) — для нас это чёрный ящик «текст → вектор».*

---

## Как распознаётся намерение

Один раз, при инициализации NPC, все намерения из базы прогоняются через эмбеддер и превращаются в векторный индекс. Дальше на каждый запрос игрока работает семантический поиск:

```
 [однократно]  намерения из базы ──▶ эмбеддер ──▶ векторный индекс

 [на каждый запрос игрока]
   «продай-ка дробовик»
        │  эмбеддинг фразы
        ▼
   семантический поиск ──▶ ближайшее намерение: «SellItem | item: shotgun»
        │
        ▼
   поставщик контекста намерения
        ├─ состояние игрока → «ранен, золота 250»
        └─ состояние NPC    → «дробовик: 12 шт, цена 300»
        │
        ▼
   контекст ──▶ в промпт модели
```

Главное свойство: **поиск идёт по смыслу, а не по словам.** Десяток формулировок одной просьбы («продай дробовик», «беру помповое», «дай двустволку») ведут к одному намерению.

---

## Откуда берётся контекст

У каждого намерения есть свой **поставщик контекста** с двумя каналами: **состояние NPC** (что у торговца на складе, почём) и **состояние игрока** (сколько золота, ранен ли). Именно они дают те самые «живые» факты — и именно здесь база смыкается с игрой.

Ключевое свойство: **откуда брать данные — решает разработчик.** Сейчас поставщик спрашивает игровую логику напрямую (инвентарь, деньги, здоровье), но с тем же контрактом «верни строку состояния» мог бы ходить в базу данных, во внешний сервис или в другой RAG. Поменять источник — локальная правка одного поставщика, не затрагивающая ни модель, ни остальной пайплайн.

---

## Что уходит в промпт

Оба канала контекста вместе с самим запросом образуют вход модели:

```
   request_of_user: «а дробовик есть?»
   state_of_user:   «ранен, денег 250»
   state_of_npc:    «дробовик: 12 шт, цена 300»
```

Модель видит только готовые строки — как разработчик их собрал, ей неважно. Так ответ NPC опирается на реальное состояние игры, а не на выдумку модели.

---

## Итог раздела

Память NPC — это RAG, встроенный в движок, но с важным сдвигом:

1. **База хранит намерения игрока, а не факты.** Факты остаются в игре и подтягиваются живьём — рассинхрону неоткуда взяться.
2. **Семантический поиск** по фразе игрока находит ближайшее намерение — по смыслу, а не по словам.
3. **Поставщик контекста** намерения отдаёт актуальное состояние NPC и игрока; источник данных — на выбор разработчика.
4. **Выбор действия — не забота базы**, это решение модели (раздел 4).

> **Сноска.** Базу знаний не пишут руками — она, как системный промпт и грамматика (раздел 4), генерируется из описания NPC в DataAsset. Сам генератор — тема части 3.

Теперь NPC знает свой мир и отвечает к месту. Но говорит он пока одинаково-ровно — характер (эмоции, голос, лицо) добавит раздел 3. (А почему модель иногда ошибается даже с хорошим контекстом — честно в разделе 6.)

## Заметки автора (не для публикации)

- В тексте намеренно без имён классов/функций (по просьбе автора — оперируем абстракциями). Ниже — привязка к коду для сверки при вычитке.
- Терминология: запись базы = **«намерение» (intent)** — то, чего игрок добивается от NPC. Заменили прежнее «тема». Если понятие всплывёт в других разделах — использовать тот же термин.
- База знаний (плагин `ULlamaPlugin`): `UULlamaKnowledgeBase::UllamaKnowledgeBaseMake/AddChunk/Dispose`; асинхронно — `InitWorkerAsync`, `UpdateKbAsync`, `SearchInKnowledgeBaseAsync` (нативные `ullama_kb_make/init/add_chunk/update/search_top_n`). Всё считается на `EAsyncExecution::ThreadPool`, результат — в GameThread.
- Данные: `UNpcKnowledgeBase::Init` читает `Resources/NPCs/<Npc>/emb/knowledge_base.json` → `FKnowledgeBaseRecord { Request(=signature), Action{Name, Parameters} }`; `GetKnowledgeBaseDataSummaries()` — строки для индекса; `GetNpcDataGetterAction(idx)` — `Action` по индексу.
- «Поставщик контекста» в тексте = `UKnowledgeBaseDataGetterBase::GetNpcState/GetUserState` (BlueprintNativeEvent, пустые в C++, расширяются в BP). Резолв по намерению: `UNPCDataAsset::GetDataGetterByName` матчит `FNpcActionTemplate.ActionTemplate.StartsWith(name + "(")`; там же лежит `ActionHandler` (исполнение — раздел 4).
- Конфиг эмбеддера: `FULlamaKnowledgeBaseConfig { ModelFilePath, LoraFilePath, QueryPrefix, GpuLayers }`. `MaxResults` поиска по умолчанию 5 (в тексте — «несколько ближайших намерений»); метрика близости — уточнить в `api.h`, если понадобится называть явно.
- `state_of_npc`: в `FUserRequestData { Context, StateOfUser, RequestOfUser }` отдельного поля нет — в схеме показан ради читаемости, вероятно уезжает через `Context`. Свериться с реальной сборкой запроса.
- База знаний генерируется автоматически из DataAsset (MLOps-пайплайн) — тема части 3.
